## Q1. Three advice strings pass the 2.10.5 rule and still read badly

Found by the 2.10.5 sweep. None of them tells a planner to change a number, so
none was changed under the rule. All three fail the plain language rule in
CLAUDE.md section 8 instead, which is judgement rather than a control.

- `VOLUME_IMMATERIAL`, do this: "Keep the line visible but direct management
  attention by materiality." Two abstractions in one sentence.
- `LONG_TAIL_CONCENTRATION`, do this: "Prioritise material exceptions first and
  retain the long tail as a footnote." A planner would not say "retain as a
  footnote".
- `insufficient_evidence`, do this: "take it out of scope for this engagement
  and say so." A planner is not in an engagement. A consultant is.

**What it blocks.** Nothing. The band can close without them.

**Recommended default.** Leave them until a planner is actually observed
stumbling on one, as happened with the seven terms in 2.10.2. Rewriting copy
nobody has failed on is how the first glossary got written.

**Cost if wrong.** A third planner reads one of the three and cannot act on it,
which costs one line of a planner test and a small follow-up story.

## Q2. The demand history is not written to the run bundle

Recorded by story 2.10.1 and unchanged since. A run reopened from a bundle
draws no sparkline and no history chart, and the detail says so where the chart
would be.

**What it blocks.** Nothing today. It would block a planner reviewing a
recorded run months later from seeing the shape of a line they are asked about.

**Recommended default.** Leave it out. Adding it is a bundle schema change, a
version bump and a golden regeneration, and the bundle already proves
everything about the run that the manifest needs to attest.

**Cost if wrong.** A reopened bundle is less useful than a live run, and the
fix is a bundle schema story rather than a repair.

## Q3. The sample portfolio cannot demonstrate most of the tool

Found on 10 September 2026 while confirming band 2.10 on the live site. Four
of the five stories were confirmed on `forecast-app/sample-portfolio.csv`. The
fifth, story 2.10.5's advice copy, was unreachable from it and had to be
confirmed with fixture 31.

**Evidence.** The real engines were run over the committed sample at the server
default analysis date with no frequency chosen, which is exactly what a visitor
gets:

| | |
|---|---|
| Lines | 4, weekly, 12 periods each |
| Bands | 4 caveated, 0 clean, 0 not usable |
| Decisions | 4 `model_eligible`, nothing else |
| Finding codes present | `HISTORY_TOO_SHORT`, `LEVEL_SHIFT` only |
| Waiting on an answer | 0 |
| Policy only | 0 |
| Outlier findings | 0 |

A visitor using the sample sees the sparklines and the in-place detail, the
ACCEPT and volume share glosses, and the portfolio band label. They cannot see
the wide interval or policy only glosses, because neither decision occurs. They
cannot see the Croston gloss, because no line is intermittent. The open items
panel shows two empty sections rather than seven lines. And nothing is flagged
as an outlier, so story 2.10.5's copy is unreadable from the sample by anyone.

The sample is the only file a prospect has. It currently demonstrates a
diagnostic that finds almost nothing.

**What it blocks.** Nothing in the build. It blocks the sample from being worth
downloading, which is a commercial question rather than an engineering one.

**Recommended default.** A new sample built to fixture 31's shape, with
commercially plausible SKU names rather than fixture codes, sized so the
portfolio lands `caveated` rather than `not usable`. Fixture 31 itself is
synthetic and already committed and would work today, but its SKU codes read as
test data and a sample that returns `not usable` is a strong first impression.
Both of those are the product owner's call, which is why this is a question and
not a change. **The sample file must not be changed without his decision.**

**Cost if wrong.** A prospect downloads the sample, sees four clean lines and
one finding, and concludes the tool has little to say. That is the opposite of
the argument the product makes.

## Q5. The expected routing generator still carries the old meaning

Raised 26 September 2026 while applying Q4.

`forecast-app/tools/make_expected_routing.py` writes `expected_routing.json`.
Its `REASON["model_eligible_wide_interval"]` still reads "demand in every period
but the size swings hard, so the interval carries the value and the point number
does not". Q4 corrected the output file, not the generator.

**What it blocks.** Nothing now. It blocks the next regeneration of the routing
expectations from being correct.

**Recommended default.** The planning session updates the generator's string to
the Q4 text in its next routing expectation change, so the generator and the
file agree again. It is their file, so it is not changed here.

**Cost if wrong.** Someone reruns the generator, the note reverts silently in
content, and only the hash test stops it, with a message that reads like
tampering rather than a stale generator.
