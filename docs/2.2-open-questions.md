# Story 2.2 open questions

Status: no question blocks the build. Each entry records what it would block, the default the build applies, and the cost if the default is wrong. `expected_routing.json` v1.0 remains authoritative for every decision, and all 14 decisions match it.

## Q1. The headline shares are 65.57 and 34.43 from exact values, not 65.58 and 34.42

Blocks: acceptance criterion 9 as literally worded.

The expectations file states 65.58 percent eligible and 34.42 percent not. Those figures are the sums of the per-SKU shares after each share was rounded to two decimals. The exact eligible share from the classification stage's six-decimal shares is 65.568708, which prints as 65.57. The same rounding explains 47.55 against the exact 47.5447 for `model_eligible` and 12.33 against the exact 12.3369 for `refused_data_quality`. Every figure is inside the 0.05 tolerance the file sets for shares, and the tests assert within that tolerance.

Default: the engine stores exact six-decimal shares and the headline prints them to two decimals, so the headline and the split by reason always agree with each other and with the classification result. The interface carries no literal share.

Recommended: restate the four affected figures in `expected_routing.json` v1.1 from exact values. No decision changes.

Cost if wrong: one hundredth of a percent on a headline, and a screen whose reason split would not sum to its own headline.

## Q2. `trailing_periods_since_last_demand` is not emitted

Blocks: nothing. The field appears in the expectations file per SKU but is not part of acceptance criterion 1.

The value is the count of periods between the last non-zero demand and the portfolio cut-off. No stage owns it. Quality measures trailing gaps from the last period present, which is exactly the known gap in section 10 of the brief, and routing may not compute a trailing gap of its own.

Default: routing does not emit the field. The reason for a discontinued line names the quality stage's own `trailing_periods` metric instead.

Recommended: move the field to the staleness story that section 10 defers, where the quality engine would own it.

Cost if wrong: none to any decision. The field would need adding to the routing result once a stage owns it.

## Q4. Resolution capture and re-run stay in Story 2.3

Blocks: nothing. The brief sets this default.

Story 1.1 records validation passes by re-running the validator with explicit options. It has no generic pass store that routing could reuse cheaply, so the second option in section 5 of the brief applies.

Default: the vocabulary is fixed in the engine and shown beside every refusal. The engine accepts an optional set of resolutions, validates each code against the refusal's own list, requires `SUPERSEDED_BY_SKU` to name a successor present in the file, records the code and any note on the line in the bundle, and reports counts by code in the manifest options. The API does not yet accept resolutions and the interface does not yet capture them.

Cost if wrong: Story 2.3 adds the form field and the pass mechanics. Nothing recorded now needs undoing.

## Q5. Which quality codes drive a `REFUSED_DATA_QUALITY` refusal

Blocks: nothing.

The quality engine bands a line not usable on three conditions that it does not name in a code of their own: a span under six periods, coverage under half, and a trailing gap of twelve periods or more. Routing may not recompute those conditions.

Default: `driven_by_finding_codes` lists the codes already on the line from `HISTORY_TOO_SHORT`, `ZERO_VS_MISSING_AMBIGUOUS`, `GAP_BLOCK` and `SERIES_DISCONTINUED`, in the order quality raised them. If none of those is present, every code on the line except `VOLUME_IMMATERIAL` is listed. Fixture 31 exercises only the first case and matches the file exactly.

Cost if wrong: a refusal could name a code that accompanied the band rather than caused it. The band itself is never in doubt because it is read, not derived.
