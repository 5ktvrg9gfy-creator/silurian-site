# Story 2.3 open questions

Status: no question blocks the build. Each entry records what it would block, the default the build applies, and the cost if the default is wrong. Section 3 of the brief is applied exactly as written: a resolution records an answer and changes scope membership, and no resolution changes a routing decision or a quality band.

## Q1. The open items list on fixture 31 carries 25.39 percent of volume, not 34.43

Blocks: acceptance criterion 7 as literally worded.

Section 4 defines the list as every line with an unresolved or deferred refusal. On fixture 31 that is the five refused lines: RTG-60403, RTG-60401, RTG-60402, RTG-60502 and RTG-60501, which carry 25.39 percent of volume. The 34.43 percent figure is the not-eligible share from the routing headline, which also counts the two `policy_only` lines, RTG-60301 and RTG-60701, at 9.04 percent between them. Those two are ineligible but not refused, and Story 2.2 fixed `policy_only` as a route with a null refusal, so they cannot sit on a list of refusals.

Default: the list follows the definition. Five lines, 25.39 percent, and the test asserts both figures from the per-line shares.

Recommended: restate criterion 7 as five lines and 25.39 percent, or, if the intent was that `policy_only` lines also wait on the planner, say so in the brief and the list would grow to seven lines and 34.43 percent. The action text already tells a planner what to do with a `policy_only` line, so the second reading is not needed to make the line actionable.

Cost if wrong: two lines appear or disappear from a client deliverable. No decision, action or resolution changes.

## Q2. A pass in the manifest references the SKU by hash, never by identifier

Blocks: acceptance criterion 6 as literally worded.

Section 3 and criterion 6 say each pass records the code, the SKU, the timestamp and the successor. The standing rule in `CLAUDE.md` says client identifiers never reach the manifest, and the manifest builder refuses any manifest containing a source SKU.

Default: the manifest pass carries `sku_sha256` and, for `SUPERSEDED_BY_SKU`, `successor_sku_sha256`, following the Story 1.5 filename rule: a reference without a readable identifier. Whoever holds the bundle can hash a SKU and match it. The readable SKU, the successor and the note live in the bundle's routing passes and on the line.

Cost if wrong: if a readable SKU were wanted in the manifest, the standing rule and the builder's refusal would both need changing. Nothing else moves.

## Q3. `SUPPLY_LONGER_HISTORY` and `SUPPLY_CORRECTED_EXTRACT` keep the line on the open items list

Blocks: nothing.

Section 3 marks every other resolution as resolved and marks these two as recorded as a data request without saying resolved. A data request is owed until the data arrives, and section 4 says the list is what the client is waiting on.

Default: these two carry the status `data_requested`, stay on the open items list labelled awaiting data, and are counted separately in the manifest outcome. `DEFER` carries the status `deferred` and also stays. Every other code carries `resolved` and leaves the list.

Cost if wrong: two lines would leave the list on a data request. The manifest counts and the per-line status would make the change a one-line edit in the effects table.

## Q4. The applied time comes from the browser and the server keeps it

Blocks: nothing.

The server is stateless and re-runs the whole pipeline with the resolutions supplied, so it cannot know when a planner picked a code except from the request.

Default: the browser stamps `applied_at` in UTC to the second when the planner applies a resolution and sends it with the run. The engine requires an ISO 8601 timestamp with an offset and refuses a resolution without one. The stage's own `started_at` and `completed_at` record when the pass was written.

Cost if wrong: a wrong clock on the planner's machine would misdate a pass. The stage times bound it.

## Q5. Applying a resolution re-runs the whole pipeline

Blocks: nothing.

Default: the browser keeps the resolutions for the current file and posts them with every quality request as `routing_resolutions`. The server validates, routes and records passes in supplied order. A new assessment from the button clears them; applying or clearing a resolution re-runs and reopens the same line. Validation, quality and classification are bitwise reproducible, so the re-run changes nothing but the routing passes.

Cost if wrong: a second or so per resolution on a large file. A pass store on the server would need the server-side state the product has deliberately avoided.

## Q6. Clearing a resolution

Blocks: nothing. The brief does not mention it.

Default: a recorded resolution shows a clear button that removes it and re-runs, because a wrong pick would otherwise need a fresh assessment. The manifest of the re-run simply omits the pass.

Cost if wrong: none. The button is one line.

## Q7. Provenance is a stage tag on every block and a title on reused metrics

Blocks: nothing. The brief leaves the form to the build.

Default: each drawer block carries a visible tag naming the stage that produced it, quality, classification or routing, and the two reused metrics carry a title stating that quality computed them and classification reused them unchanged. The engine also publishes `statement_sources`, a field-to-stage map, in the routing result so a bundle reader can do the same.

Cost if wrong: presentation only.

## Q8. The `refused_data_quality` action names the specific request from the quality codes on the line

Blocks: nothing.

Section 2 says to name the specific request. Routing may not recompute the condition, so it reads the codes and metrics quality already raised.

Default: `HISTORY_TOO_SHORT` with the engine's resolvable flag false asks for confirmation that the line is genuinely new and names the span and the quality threshold; with the flag true it asks for more periods. `ZERO_VS_MISSING_AMBIGUOUS` asks for a corrected extract and names the coverage. `GAP_BLOCK` asks for the block. Any other driver asks for a corrected extract that settles it.

Cost if wrong: wording only. The decision and refusal are unchanged.

No forecasting method or launch route runs. `SUPERSEDED_BY_SKU` records the successor as a link and chains no history. No cost or margin appears. The staleness gap, Story 2.6, is untouched: RTG-60602 still routes as eligible with four trailing zero months.
