## 1. What this story is

Every SKU gets a routing decision, a reason, an eligibility flag, and where it is refused, a refusal carrying a closed list of resolutions.

**Routing records. It does not run anything.** No forecast, no baseline, no method call. If a method executes anywhere in 2.2, scope has leaked into sprint 3.

**Routing also computes nothing.** It reads `demand_class` from classification and the band, the finding codes and `SERIES_DISCONTINUED` from quality. It does not recompute a trailing gap, an ADI, a CV squared or a coverage percentage. This is the same rule that governed 2.1, and the same test applies: every number routing shows must trace to a value another stage owns.

## 2. The decisions

Seven, closed. Full definitions in the routing table; the operative summary:

| Decision | Eligible |
|---|---|
| `model_eligible` | Yes |
| `model_eligible_wide_interval` | Yes |
| `intermittent_methods` | Yes |
| `policy_only` | No |
| `insufficient_evidence` | No |
| `refused_data_quality` | No |
| `discontinued_confirm_status` | No |

**Precedence, in order.**

1. A line carrying `SERIES_DISCONTINUED` routes to `discontinued_confirm_status`, whatever its class and whatever its band.
2. Otherwise a `not_usable` band routes to `refused_data_quality`, whatever its class.
3. Otherwise the demand class decides, including unclassifiable to `insufficient_evidence`.

**A caveated band never reroutes.** It attaches to the decision and is shown beside it.

**ABC volume class never affects the decision.** It orders attention, not judgement.

**The portfolio band never affects a line decision.** Fixture 31's portfolio band is `not_usable` at 55.27 percent flagged volume, and not one per-line decision depends on it. If wiring the portfolio band into a line decision would make anything simpler, it is the wrong simplification.

**`policy_only` is a route, not a refusal.** It is ineligible and its `refusal` is null. A lumpy line is not a data problem and must not be presented as one.

## 3. Reconciling `resolvable` with the resolution vocabulary

The quality engine already exposes a `resolvable` flag per finding. On fixture 31 it marks `HISTORY_TOO_SHORT` as `resolvable: false` while my vocabulary offers `SUPPLY_LONGER_HISTORY` and `TREAT_AS_NEW_LINE` for that same line. Two parts of the system appearing to disagree about whether something can be resolved is the 1.6 defect wearing a new coat, so settle it before writing code.

They are compatible, because they answer different questions:

- The engine's flag answers: **can a user decision change this band in this run?** For a five period history, no. Nothing the client says makes five points into a usable history.
- A routing resolution answers: **what happens to this line next?** Supply a different extract and re-run, treat it as a launch and forecast by analogue, take it out of scope, or defer.

So the rule is: **a routing resolution never changes a quality band.** It changes scope, changes the route, or asks for a new run. Any resolution that would silently flip a band is wrong and must not be built.

Two consequences for the interface. Do not use the word "resolve" for both concepts on the same screen. And the resolution list on a `resolvable: false` line must not imply that picking an option makes the finding go away.

## 4. What each line carries

- `decision`, one of the seven
- `reason`, one sentence naming the numbers that drove it. `reason_must_convey` in the expectations file gives the substance for each decision, not the wording. Write the wording; match the house register.
- `forecast_eligible`, true or false
- `quality_band_at_decision`, the approved exception to implementation default 4, because a decision that cannot show its input is not reproducible
- `refusal`, null unless refused, otherwise a code, the quality finding codes that drove it, and the resolution options

Quality codes appearing inside a routing refusal are **references, not emissions**. Routing raises none of them, so the 1.6 cross-stage test still holds and must still pass.

## 5. Resolutions

Closed vocabulary, in `resolution_vocabulary` in the expectations file. Every list ends with `DEFER`.

Rules:

- The code is required. A free-text note may accompany it and carries no behaviour.
- The note is client data. It belongs in the bundle and never in the manifest.
- `SUPERSEDED_BY_SKU` requires a successor **selected from the SKUs present in the uploaded file**, never typed.
- A supplied resolution produces a new pass recorded in the manifest options, as story 1.1 does for validation.
- `DEFER` is a legitimate answer. Unresolved lines appear on an open items list and are not a failure state.

**Scope question, with a default.** Story 1.1 already implements resolution passes for validation. If that mechanism generalises cheaply, capture the resolution and re-run in this story. If it does not, define and display the vocabulary, record a supplied code, and move capture and re-run to 2.3. **Default to the second if it is at all close.** The vocabulary is what must be fixed now; the plumbing can follow.

## 6. Manifest and bundle

Routing is a stage, on the same footing as validation, quality, classification and forecast.

- `stage: "routing"`, added to the enum.
- `input_ref` is the classification stage's `output_ref`. Assert that edge, as 2.1 does for quality to classification.
- `output_ref` points at `routing_result`.
- `options` carries the routing table version, the precedence order and the resolution vocabulary as applied.
- `outcome` carries **counts and codes only**: decision counts, eligible and ineligible counts, refusal code counts. No SKU codes, no volumes, no shares.

`results.routing` becomes a required bundle key whenever a routing stage appears in the manifest, and absent when it does not, with the conditional written both ways.

Bump both schemas one minor version from whatever `main` currently carries, and state both numbers in the pull request description.

## 7. Interface

Follows the 2.0 structure. Self-contained panel components, tokens from `index.html`, no new colours, no second typeface.

**The grid** gains a decision column and a filter by decision. Sorting, filtering and search survive a panel switch, as before.

**The drawer** gains the decision, the reason and, on a refused line, the refusal with its resolution options displayed. The **what** and **so what** already exist from 2.1. The **do this** slot stays empty: that is story 2.3, and filling it here would write an action before the action view exists.

**The headline.** The routing panel opens with one sentence: **65.57 percent of volume is forecast eligible, 34.43 percent is not**, followed by the split by reason. That is the first sentence in this product a client would repeat in their own meeting, so it gets the position and the weight.

**Colour follows the 2.0 rule.** Orange as a mark or a field, never a seven state palette. The decision is written on every row. Removing colour entirely must leave the screen fully readable.

## 10. Known gap, recorded not fixed

Staleness and discontinuation are measured on the last period present, not the last period with demand. A line that reports explicit zeros for twelve months is therefore never flagged as discontinued, and plenty of ERP extracts look exactly like that. RTG-60602 in fixture 31 demonstrates it: four periods with no demand, zero rows present, and a clean band.

This is a quality engine question, it changes fixture 30 and 31 expectations, and it overlaps `ZERO_VS_MISSING_AMBIGUOUS`, so it needs its own story with a stated precedence between the two findings. Do not fix it inside 2.2.
