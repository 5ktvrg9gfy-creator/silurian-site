## 2. Story 2.9.1, one `:root`

There were two `:root` blocks. The first carried the abandoned Claude Design
palette and the second overrode three of its values. The three overridden
values were dead. The other five were not: `--bg`, `--muted`, `--good`,
`--warn` and `--bad` were declared **only** in the first block, so deleting it
outright, which is what "delete the dead first `:root` block" reads as, would
have taken the three status colours with it and failed
`test_status_colours_match_assay` on the way out.

They are now one block, carrying every live value once.

Because custom properties resolve at use time from the final cascade value,
every `var()` in the file already saw the second block's values. Consolidating
therefore changes nothing that renders, and section 4 below shows that it
did not.

## 9. Addendum, 16 September 2026: section 9 amended and the tests changed

Added to this file rather than a new one, because it is the same pull request
and the same stylesheet.

### The order this was done in

1. The build session reported that the theme could not be applied without
   breaking `CLAUDE.md` section 9, and recommended against applying it.
2. **The product owner amended section 9.** Zero radius remains the rule for
   the marketing site. Assay is a documented exception: 4px on cards, buttons
   and inputs, 3px on badges, never higher than 4px; one shadow step at the
   changeset's values with no second step; 1px rules inside the app with the
   2px ink rule retained on the page header only.
3. **Only then were the tests changed.** The amendment is recorded in
   `CLAUDE.md` as section 9a, with the date, who made it, and what it replaced.

That order is the whole point. A build session editing a control to make its
own work pass is the move section 4 calls unrecoverable. A product owner
changing the rule the control enforces, and the control following, is not the
same act, and the difference is only legible if the record shows which came
first.

### What changed in the tests

| Was | Is |
| --- | --- |
| `test_workspace_ui.py` asserted the literal `*{border-radius:0!important}` | `test_no_radius_exceeds_the_assay_bound` scans every `border-radius` declaration and fails on anything above 4px |
| `test_access_gate.py` asserted the same literal | `test_the_gate_controls_declare_their_own_radius_within_the_bound` requires the two controls to declare a radius and holds the same bound |

The bound replaced the pinned value deliberately. The amendment's load bearing
half is "never higher than 4px", because that is the half that stops the
exception widening into a generic dashboard one screen at a time. A test
pinning `4px` would pass a page that had quietly moved to `4px` everywhere
including badges, and would fail the moment the theme is built correctly. A
bound holds before the theme is built, after it is built, and against the next
restyle.

Five tests were added and the suite went from 263 to 268.

### The new controls were proved able to fail

Not against a synthetic string alone. Against the real files:

```
planted border-radius:8px on .filter-chip in forecast-app/static/index.html
  -> FAILED (failures=1)   ['8px'] != []

removed the explicit radius from the gate controls in access_gate.py
  -> FAILED (failures=1)   'border-radius:0' not found in the gate page
```

Both files were restored and the suite is green. The test also carries two
table driven probes: `8px`, `50%`, `0.5rem`, `6px 6px 0 0` and `4.5px` must
each be caught, and `0`, `0px`, `3px`, `4px`, `4px 4px 0 0` and `0!important`
must each be permitted. A percentage is a finding on purpose, because the rule
is a px bound and a value the scan cannot measure is not evidence that the
bound holds.

### Removing the universal reset changed nothing on screen

`*{border-radius:0!important}` was removed from the Assay page and the gate
screen. It had to go: `!important` on the universal selector is not a default
a later rule can beat, so a card written as `border-radius:4px` would have
rendered square regardless, and the amended rule would have been
unimplementable.

Removing it is only safe because story 2.9.3, earlier in this same pull
request, gave every control an explicit `border-radius:0`. The reset's real
job was defending against platform control radii, and that job now has an
owner. The gate screen's two controls were given the same explicit
declaration for the same reason.

Measured, not assumed:

```
1174 control readings across 10 screens, with and without the reset
NO COMPUTED CHANGE: colour, fill, radius, appearance and border colour
                    identical on every reading
distinct radius values computed page-wide: ['0px']
```

Rendered text on all 11 screens is still identical to the unmodified app.
Eight of the ten screenshots are pixel identical. The other three differ only
inside an 8px tall strip in the page footer and the provenance grid, which is
where the run id and the manifest hash are printed, and those are new on every
run. The strip was cropped and read at 2x: same type, same weight, same
colour, same position, different hash.

### What this addendum does not do

**The theme is still not built.** The rule now permits it. Nothing in this
pull request applies 4px to a card, a shadow to a panel, or the slate palette
to anything. Q3 in `docs/assay-theme-open-questions.md` is the reason: the
changeset is a mock for an information architecture Assay does not have, and
somebody has to decide line by line what its rules mean for the screens that
exist. That decision is the planning session's.

**Two new questions came out of the amendment**, Q8 and Q9 in the same file.
Q8 is the one that matters: Assay already carries a `box-shadow` on the sticky
run context bar, and section 9a now says there is one shadow step and no
second. Either that bar is the second step, or the rule means card elevation
only and should say so. The shadow half of section 9a cannot be tested until
it is decided, and an untested half of a rule is how the first one drifted.
