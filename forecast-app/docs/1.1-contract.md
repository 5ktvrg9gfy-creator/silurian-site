# Story 1.1 Phase 1 proposed contract

## Pure validation boundary

The validator will be a pure function with this conceptual interface:

```python
validate_csv(raw: bytes, options: ValidationOptions) -> ValidationResult
```

`ValidationResult` will contain:

- `verdict`: `accept`, `accept_with_warnings` or `reject`
- `findings`: a deterministically ordered list of `Finding`
- `normalised_rows`: contract rows produced only by explicit or unambiguous transformations
- `metadata`: detected encoding, delimiter, header row, input shape and row counts

No detector will read files, call the network, log, use randomness or call a forecasting provider.

## Finding interface

The build will use the brief's finding shape without amendment:

```text
Finding
  code: string
  severity: blocking | warning | info
  stage: bytes | shape | columns | rows | keys | series
  scope.level: file | column | sku | row
  scope.ref: string or null
  count: integer
  examples: up to five source-row examples
  detail: factual description
  action: one next step
  resolution: decision required to start a new pass, or null
  auto.applied: boolean
  auto.transform: string or null
  auto.reversible: boolean
```

Source rows count from one and include any preamble. Automatic transformations always create a finding. Findings sort by severity, stage, code and scope reference using explicit enum order, then by the first source row as a deterministic tie-breaker.

Every blocking finding must name its resolution path. A user cannot override a block. The user resolves it through an explicit option recorded in a new validation pass. The only exceptions are a wrong file and required information that is absent from the source.

## Verdict logic

```text
any blocking finding -> reject
no blocking finding and any warning -> accept_with_warnings
information findings only -> accept
no findings -> accept
```

An accepted file may therefore contain information findings describing reversible automatic transformations.

## Detection order and stop behaviour

The build will use the required order:

1. Bytes
2. Shape
3. Columns
4. Rows
5. Keys
6. Series

The first unresolved blocking root cause in the bytes or shape stage stops later stages. A stage may emit multiple findings that describe the same inspected structure before stopping, provided no later stage runs. A controlled second validation with an explicitly approved encoding or reshape option is a new run, not a continuation hidden inside the first run.

## Normalised row contract

Each accepted long-format row will contain:

- `source_row`
- `sku`
- `date`
- `demand`
- optional `uom`
- optional `customer`
- optional `site`
- optional `record_type`

The validator will preserve original raw values in transformation evidence. It will not merge suspected aliases, choose between ambiguous quantity columns, infer conflicting date orders, mix record types, select a granularity or rescale a suspected unit change.

## API and forecasting boundary

`app.py` will validate immediately after reading the uploaded bytes. A rejected result returns structured findings and never calls `parse_demand_csv`, `parse_portfolio_csv`, `analyse`, TimesFM or BigQuery.

Accepted normalised rows will be adapted into the application's existing `DemandSeries` or `PortfolioItem` structures. Forecasting and inventory logic remain outside this story.

## Test contract

Tests will use the existing `unittest` style. Assertions will cover:

- expected verdict per fixture
- every expected finding code
- zero findings for the clean control
- deterministic byte-identical serialisation and ordering
- stage stop behaviour
- 50,000 rows under five seconds
- message rendering reviewed through golden files, without exact wording assertions in detector tests
