# Story 1.1 open questions

## Status

Questions Q1 to Q14 were answered authoritatively in package version 1.1 and are closed. The decisions below replace the earlier recommended defaults.

- Q1: Fixture 05 rejects on `DUPLICATE_KEY_CONFLICT`.
- Q2: Fixture 06 uses guided passes and obeys the stage stop rule.
- Q3: Exact duplicates auto-deduplicate only at period grain. Transactional duplicates remain with a warning.
- Q4: Wide format rejects first and requires explicit unpivot, period and fiscal-year decisions.
- Q5: Matching negative reversals net automatically. Unmatched returns remain separate and default out of demand unless confirmed.
- Q6: Blocks cannot be overridden. Every block requires resolution through a new pass, except unusable files or absent required information.
- Q7: Validation results are not cached or reused.
- Q8: Story 1.1 reports history length as fact. Sprint 2 decides forecastability.
- Q9: HTTP upload limit becomes 4 MB. The 50,000-row validator test remains outside HTTP.
- Q10: The API returns a downloadable JSON run record. Nothing is stored server side.
- Q11: `as_of_date` is an explicit validation option. Fixtures use `2026-08-01`.
- Q12: Exact built-in synonyms and replayable per-run mappings are used. Non-canonical mappings are reported.
- Q13: Information findings remain an `accept` verdict.
- Q14: Browser content type is metadata only. Bytes determine validity.

Two future confirmation-screen specifications remain open but do not block the first Phase 2 implementation:

## Blocking contract decisions

Q1. Should `05_duplicates_and_aliases.csv` be rejected because it contains a conflicting duplicate key, despite the fixture-level verdict saying `accept_with_warnings`?
    Blocks: verdict tests and `DUPLICATE_KEY_CONFLICT`
    My recommended default: reject the file, because two quantities for the same SKU and date cannot both become one trusted observation
    Cost if wrong: the implementation will either contradict the fixture verdict or allow an unresolved demand conflict into forecasting

Q2. For `06_semicolon_latin1.csv`, should the first run stop after byte-stage findings, with downstream codes produced only after the user approves a latin-1 re-read?
    Blocks: stop-rule tests and the expected-code assertion for fixture 06
    My recommended default: first run rejects with `ENCODING_NOT_UTF8` and `DELIMITER_NOT_COMMA`, then an explicit re-read option starts a second validation that may emit later-stage findings
    Cost if wrong: either the validator violates the stop rule or the first run cannot match every code currently listed for fixture 06

Q3. Should exact duplicate rows always be an information finding when automatically removed?
    Blocks: `DUPLICATE_ROW_EXACT` severity in fixtures 02 and 05
    My recommended default: information severity, with `auto.applied=true`, a reversible de-duplication transform and the affected count
    Cost if wrong: fixture 02 currently calls the same condition a warning, producing inconsistent verdict behaviour

Q4. Should a wide-format file be rejected until the user explicitly approves unpivoting, or may the validator auto-unpivot and return `accept_with_warnings`?
    Blocks: fixture 04 verdict and the boundary for unambiguous transformations
    My recommended default: reject the first run and offer one explicit unpivot action; the approved second run reports the reshape and excluded totals as information findings
    Cost if wrong: automatic reshaping may make an irreversible business assumption about period columns and totals

## Product decisions

Q5. Should negative quantities be retained and netted within the period, or excluded as returns?
    Blocks: `VALUE_NEGATIVE` normalisation and later aggregation
    My recommended default: retain the negative value, flag it as a warning and net it within the period only after the user confirms that returns belong in demand
    Cost if wrong: excluding returns overstates net demand, while netting operational reversals may understate gross demand

Q6. May a user override a blocking finding through explicit acknowledgement?
    Blocks: API control flow and audit behaviour
    My recommended default: no override in story 1.1; blocking always prevents forecasting
    Cost if wrong: a convenient override weakens the core trust promise and requires a stronger audit and permission model

Q7. Should the same file uploaded twice reuse a previous validation result?
    Blocks: caching and file fingerprinting
    My recommended default: no reuse in story 1.1; validate every upload deterministically
    Cost if wrong: repeated validation uses more compute, while caching introduces persistence, invalidation and privacy questions

Q8. Should story 1.1 report short history only as a warning fact, leaving method suitability to Sprint 2?
    Blocks: `HISTORY_TOO_SHORT`, `SINGLE_OBSERVATION_SERIES` and the current 12-period parser rule
    My recommended default: yes; validation reports the facts, and the existing forecast endpoint separately refuses series that cannot yet be routed safely
    Cost if wrong: story 1.1 begins making forecasting-method decisions that the brief places in Sprint 2

Q9. How should the 50,000-row performance requirement interact with the current 2 MB upload limit?
    Blocks: production API acceptance test
    My recommended default: raise the upload limit to 10 MB after validation performance passes, while retaining the 50,000-row test independently of HTTP upload size
    Cost if wrong: a validator may meet the performance target but reject realistic client files before validation begins

Q10. What qualifies as a reopenable run record when the application has no persistence layer?
    Blocks: the run-record part of the definition of done
    My recommended default: return a serialisable validation record in the API response and defer week-later persistence to the security and workspace sprint
    Cost if wrong: adding storage now expands story 1.1 into authentication, retention, privacy and data-deletion design

Q11. What date should define `DATE_FUTURE` for deterministic fixture tests?
    Blocks: `DATE_FUTURE` and repeatable tests
    My recommended default: require an explicit `as_of_date` in `ValidationOptions`; the API supplies the current date, while fixtures use a fixed date stored with the test expectations
    Cost if wrong: tests and historical validation results change as the calendar advances

Q12. Should client-defined column synonyms be supplied as run options or maintained as application configuration?
    Blocks: column mapping interface and extension audit trail
    My recommended default: built-in exact synonym table plus explicit per-run mappings; every non-canonical mapping emits an information finding
    Cost if wrong: global configuration can silently change how an old file is interpreted, while per-run mapping adds one user step

## Recorded defaults that do not block Phase 2

Q13. Should information findings count as a clean acceptance?
    Blocks: none if the verdict logic above is accepted
    My recommended default: yes; `accept` means no warning or blocking findings, not necessarily an empty findings list
    Cost if wrong: automatic but reported transformations would incorrectly create `accept_with_warnings`

Q14. Should browser-reported content type remain a blocking gate?
    Blocks: none
    My recommended default: no; use it as metadata only and validate the bytes, because browsers and export tools label CSV files inconsistently
    Cost if wrong: valid CSV content may be rejected before the strict validator inspects it
