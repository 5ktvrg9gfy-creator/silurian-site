# Story 1.1 Phase 0 survey

## 1. Current path

| Path | Purpose | Verdict |
|---|---|---|
| `static/index.html` | Collects the single-SKU or portfolio CSV and submits it as `FormData` to `/api/analyse` or `/api/analyse-portfolio`. It renders one error string from `detail`. | extend |
| `app.py` | Accepts `UploadFile`, checks the reported content type and 2 MB size limit, reads bytes, calls a parser, then calls analysis. It converts `ForecastError` to HTTP 400 and other failures to HTTP 503. | extend |
| `forecast_engine.py::parse_demand_csv` | Decodes UTF-8 with optional BOM, uses `csv.DictReader`, requires exact `sku`, `date`, `demand` headers, parses one SKU, sorts dates and returns `DemandSeries`. | replace |
| `forecast_engine.py::parse_portfolio_csv` | Decodes UTF-8 with optional BOM, requires six exact headers, parses and groups up to 250 SKUs, then returns `PortfolioItem` objects. | replace |
| `forecast_engine.py::analyse` | Back-tests baselines, calls the configured forecast provider and applies inventory logic. It assumes the series has already been validated and ordered. | keep |
| `forecast_engine.py::analyse_portfolio` | Calls `analyse` for each parsed portfolio item and ranks results. | keep |
| `bigquery_timesfm.py` or `TimesFMProvider` | Receives numeric history only after parsing and requests the model forecast. | keep |
| `tests/test_forecast_engine.py` | Covers the clean happy path, multiple-SKU rejection and portfolio ranking using `unittest`. | extend |

Current request path:

`browser form -> FastAPI upload -> raw bytes -> parse function -> DemandSeries/PortfolioItem -> analyse -> provider.forecast`

## 2. Validation already present

The API checks the browser-reported media type:

```python
if file.content_type not in {"text/csv", "application/vnd.ms-excel", "application/octet-stream"}:
    raise HTTPException(status_code=415, detail="Upload a CSV file")
```

It rejects files larger than 2 MB:

```python
raw = await file.read()
if len(raw) > 2_000_000:
    raise HTTPException(status_code=413, detail="The CSV must be smaller than 2 MB")
```

Both parsers enforce UTF-8 decoding and exact required headers. The single-SKU parser also requires at least 12 rows, one SKU and unique dates. The portfolio parser requires at least 12 rows per SKU, no duplicate dates, non-negative numeric inputs and no more than 250 SKUs.

Row failures are collapsed into a generic message:

```python
raise ForecastError(f"Invalid value on CSV line {line_number}")
```

This names a line but not the column, raw value or required fix. Date parsing uses ISO format only. Numeric parsing uses `float`. Rows are sorted silently. A UTF-8 BOM is removed silently by `utf-8-sig`. No delimiter, preamble, wide-format, alias, granularity, record-type or series-integrity checks exist. The UI displays only one exception string, so it cannot render structured findings.

## 3. Current data structure and assumptions

The single-SKU parser returns:

```python
DemandSeries(sku: str, dates: list[date], demand: list[float])
```

The portfolio parser returns a list of:

```python
PortfolioItem(series: DemandSeries, current_inventory: float,
              confirmed_inbound: float, safety_stock: float)
```

The forecast call assumes dates and demand are aligned, chronologically sorted, numeric, non-negative and semantically actual demand at one consistent unit and granularity. It has no access to source rows or transformations. Once parsing succeeds, there is no audit trail showing how the uploaded bytes became the numeric series.

## 4. Insertion point

Validation should run in `app.py` immediately after the byte-size check and before either parser or any call to `analyse`. A new pure validation module should accept bytes and explicit options, then return a deterministic validation result containing verdict, findings and normalised rows.

Upstream changes:

- Keep upload and size handling in FastAPI.
- Stop trusting the browser media type as proof of structure.
- Pass raw bytes and explicit user-approved options to the validator.

Downstream changes:

- Build `DemandSeries` and `PortfolioItem` only from accepted normalised rows.
- Do not call `analyse` when verdict is `reject`.
- Return structured findings to the UI for row-level rendering.
- Carry warnings and automatic transformations in the analysis response or run record.

## 5. Conflicts and risks

1. The brief requires a pure validator, but current parsing and validation are combined in `forecast_engine.py`. Separating them is an architectural change, although forecasting code can remain untouched.
2. The current single-SKU contract requires 12 periods and exactly one SKU. The fixtures include portfolios, short histories and single-observation series that must return warnings. Story 1.1 therefore needs a validation contract that is broader than the current single-SKU execution contract. Forecast routing remains a later decision.
3. The current 2 MB limit may prevent a 50,000-row file reaching validation through the API. The pure-function performance test can still run, but production acceptance requires a later decision on the upload limit.
4. The definition of done says findings must persist in a run record, but the application currently has no run persistence. The brief also says persistence beyond the run record is out of scope. A response-carried run record can be implemented, but reopening it a week later requires storage that does not exist.
5. Fixture `05_duplicates_and_aliases.csv` is declared `accept_with_warnings`, while `DUPLICATE_KEY_CONFLICT` is tagged `reject` and the detection notes call conflicting duplicate keys blocking. The verdict source of truth is therefore internally inconsistent and must be resolved in Phase 1.
6. Fixture `06_semicolon_latin1.csv` expects both an encoding rejection and downstream delimiter, date, numeric and column findings. The stop rule says an unresolved stage A rejection must prevent downstream findings. The expected code list and stop rule cannot both be satisfied without defining a controlled re-read phase.
7. The brief says exact duplicates auto-deduplicate, while fixture `02` tags `DUPLICATE_ROW_EXACT` as a warning. The severity needs agreement before snapshot-stable findings can be implemented.
