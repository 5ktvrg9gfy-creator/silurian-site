# Story 1.2 Phase 0 survey

## Current 1.1 output

`validate_csv(raw, options)` is already the correct boundary for story 1.2. It returns one immutable `ValidationResult` containing:

- `verdict`: gate outcome, separate from any future quality band.
- `findings`: stable, ordered 1.1 findings with code, severity, stage, scope, evidence, action, resolution and auto-transformation details.
- `normalised_rows`: long-form records with `source_row`, `sku`, ISO `date`, numeric `demand` and any supplied `uom`, `customer`, `site` or `record_type`.
- `metadata`: header row, encoding, delimiter, shape, row counts and the current grain classification.
- `run_record`: schema version, source SHA-256, validation options, verdict, findings, row counts and metadata.

The quality report can derive every story 1.2 metric from `normalised_rows` without reading or parsing the source file again. Coverage, continuity, zero facts, ADI, CV squared, materiality, outliers, shifts and staleness all require only SKU, date, demand and the agreed `as_of_date`.

The transformation log is not a separate collection. It survives inside the ordered findings through `auto.applied`, `auto.transform` and `auto.reversible`. Story 1.2 can reference it but must not repeat the transformations or reinterpret the raw file.

## Where the normalised dataset lives

The dataset exists in memory on `ValidationResult.normalised_rows`. It is retained for the forecasting path, but the public `/api/validate` response deliberately omits it. A new quality endpoint can call `validate_csv` once and pass the returned `ValidationResult` directly to a pure quality function. No API exposure or temporary file is required.

The shape is one row per accepted observation at the validated grain. Dates are ISO strings and demand is numeric. Exact period-grain duplicates and matched reversal pairs have already been removed and recorded by 1.1.

## Grain, as-of date and audit survival

- **Grain:** only `period` or `transactional` currently survives in metadata. Story 1.2 needs the actual calendar grain, such as month, week or day, inferred from modal spacing and available as a user override. This must be added to the validation result or to a quality-context object without reparsing the file.
- **As-of date:** it survives in `run_record.options.as_of_date`. The API currently overwrites every supplied value with the server date. Story 1.2 fixtures require a deterministic date and the control requires `2026-01-01`, so the endpoint must accept an explicit authorised override and record it.
- **Transformations:** transformation details survive in findings and the run record. A small accessor may expose them as a list for the report object, but it must reuse the existing findings.

## Friction with the current build

1. 1.1 already emits several series-level warnings, including short history, discontinued series and zero-versus-missing ambiguity. Story 1.2 must compute its own portrait from normalised data and must not relabel those validation messages as quality findings. The two models should share facts where practical, not presentation or severity.
2. The current grain label is too coarse for calendar coverage calculations.
3. The server-date override prevents deterministic staleness and trailing-gap results.
4. The quality report needs the accepted normalised rows in the same request. The existing response helper omits them, which is correct for the browser but means the new endpoint must retain the in-process `ValidationResult`.
5. The portfolio forecast still reparses accepted raw bytes through `parse_portfolio_csv`. Story 1.2 must not copy that pattern. It should consume `ValidationResult.normalised_rows` directly.
6. Story 1.1's pack-factor detector will see fixture 22 before quality analysis. The planted 1.6 level shift should pass because it is not within the pack-factor tolerance, but this needs an explicit regression test.

No new runtime dependency is required. The standard library is sufficient for all specified metrics and detectors.
