# Story 1.3, amendments after the survey and contract

All four Phase 1 decisions are approved as taken. Q3 caught a real contradiction in my acceptance criteria and the resolution is correct. The schema and both golden manifests have been rebuilt to v1.1 and ship with this note.

Three things the survey has surfaced that the contract does not yet cover. The first would invalidate the determinism measurement, so read it before running the ten repeats.

---

## 1. The ten-repeat measurement will measure the BigQuery cache, not the model

**Stop before running it.** BigQuery caches query results by default. Ten identical `AI.FORECAST` queries over identical input can return one cached result nine times. The comparison then shows zero variance, the class is set to `bitwise`, and the manifest carries a confident claim that has measured nothing.

That is precisely the overclaim this story exists to prevent, and it would be almost impossible to detect afterwards.

Required:

- Disable the query cache for every measurement run. `use_query_cache: false` on the job configuration, or `--use_cache=false` from the CLI. Confirm from the job metadata that `cacheHit` is false on all ten, rather than trusting the flag.
- Record it. `determinism.measurement.provider_cache_disabled` is now a required field, and the schema will not accept a `bitwise` or `tolerant` class without the whole measurement block.
- Set `bigquery_use_query_cache: false` in the forecast stage options for measurement runs, so the manifest shows the condition the measurement holds under.

The schema now rejects a measured class with no evidence. I have tested that: flipping the golden to `bitwise` without a measurement block fails validation.

**Zero denominator rule**, which the contract asked for and left open. Where the reference value is zero, report the absolute difference only, exclude the point from the percentage statistic, and count those points separately in `zero_denominator_points`. Never substitute a small epsilon, which manufactures a percentage that looks reassuring and means nothing.

---

## 2. Managed model drift, which the version string will not reveal

The survey states the position correctly: Google manages the weights and does not expose a revision. The consequence deserves stating more sharply than "record the limitation".

Google can update the model behind `TimesFM 2.5` without changing the friendly version string. A run in October may not reproduce a run in August, **and nothing in the manifest as specified would show it.** The ten-repeat measurement tells you about variance within a moment. It tells you nothing about drift across months, and a diagnostic engagement is exactly the setting where somebody re-runs an analysis a quarter later and expects the same answer.

**Mitigation, and it is cheap: a reference canary.** Hold one fixed synthetic series, send it through the same provider path on a schedule and at the point of every run, hash the output, and compare it to a stored baseline.

`model.reference_check` is now in the schema:

- `reference_series_sha256`, the fixed input
- `reference_output_sha256`, what the provider returned this time
- `baseline_output_sha256`, what it returned when the baseline was set
- `status`, one of `match`, `drift_detected`, `not_run`
- `checked_at`

Every manifest then carries evidence that the managed model still produced the known answer for a known input at that moment. When the hashes diverge and the version does not, you know the provider changed the model, you know roughly when, and you can tell a client so before they find it themselves. Without it, the first sign of drift is a client disagreeing with a number you cannot defend.

Use a synthetic series with no client data in it, so the canary can run on a schedule without touching anyone's data.

## 3. Two items that belong to story 1.5, raised now because they are cheap now and expensive later

The survey mentions `BIGQUERY_LOCATION` defaulting to `US`. That has consequences beyond configuration.

**Data residency.** Client demand data, even anonymised, transiting to a US BigQuery region is a procurement question for any UK or EU pharma client, and it will be asked by someone whose job is to ask it. Changing the region now costs a config value. Explaining it during a security review, after a client has already sent data, costs the engagement. Set it to a UK or EU region unless there is a reason not to, and record the region in the manifest, which the schema already does.

**Retention.** Story 1.5 states that files are not retained. `AI.FORECAST` means data leaves the application and enters BigQuery, which creates temporary tables and job results with their own lifecycle. The no-retention claim has to account for that or it is not accurate.

Needed for 1.5, not for this story: explicit deletion of any dataset or table created for a run, a stated default table expiry, a position on BigQuery job result retention, and one honest sentence about the sub-processor. "We do not retain your data, and our forecasting provider is Google BigQuery in the UK region, where working data is deleted at the end of each run" is a perfectly good answer. Silence is not.

The manifest itself stays clean either way, since it holds no client data. That property is worth more here than it looked when I specified it.

## 4. Smaller corrections, already applied to the schema

- **Context window honesty.** Pinning 512 is right, and 512 over 35 monthly points would read as more history than exists. `context_points_supplied` now records the min, median and max points actually provided per series. On the golden that is 8, 35 and 35, which tells the truth alongside the pinned window.
- **Confidence level against quantiles.** A bare `0.9` is ambiguous between a 90 percent interval and a 90th percentile. Both are now recorded: `confidence_level` as requested, and `interval_bounds` as the explicit quantiles it resolves to, `[0.05, 0.95]`.
- **`provider_limitations` is now a required array**, so a limitation is a first-class statement rather than a sentinel that a reader has to interpret.
- **Sentinels.** `provider_managed_not_exposed` for checkpoint, backend and precision. Environment placeholders are now `SUPPLIED_BY_DEPLOYMENT`, which reads as a deployment task rather than an oversight, and the no-placeholder test should reject both that string and `REPLACE_WITH_ACTUAL`.
- **`git_commit: "0000000"`** in the goldens is a schema-valid sentinel only. It still has to fail the no-placeholder test, so assert on the value, not just on the pattern.

## 6. One addition to acceptance

Add a thirteenth criterion: **the reference canary runs, records a baseline, and a deliberately altered baseline produces `drift_detected` rather than passing silently.**

Same principle as the corrupted reference test. An integrity check nobody has seen fail is not an integrity check.
