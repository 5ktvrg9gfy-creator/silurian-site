# Story 1.3 run-manifest contract

## Boundary

The manifest builder binds completed stage records into one provenance object:

`build_run_manifest(run_context, stage_records, environment) -> RunManifest`

It does not parse source data, validate a file, assess quality or call a forecasting provider. Each stage supplies its already-computed options, outcome, timing and artefact references.

The builder fails closed if schema validation, reference verification, placeholder detection or the no-client-data assertion fails.

## Run definition

One explicit user action creates one run:

- Validate: validation stage.
- Assess quality: validation and quality stages.
- Forecast: validation and forecast stages.
- Quality-routed portfolio forecast: validation, quality and forecast stages.

Only executed stages appear. A rejected run contains the source and rejected validation stage, with no quality or forecast stage.

## Canonical JSON

All artefact hashes use UTF-8 canonical JSON with sorted keys, separators `,` and `:`, and no insignificant whitespace. Source files are hashed as raw bytes before decoding or transformation.

Dates and timestamps are serialised as ISO 8601 strings before hashing. Non-finite numbers are prohibited.

## Integrity hashes

- `manifest_sha256`: SHA-256 of the complete manifest with this field set to an empty string. It identifies one exact run and includes timestamps and run identity.
- `content_fingerprint_sha256`: SHA-256 of the manifest after clearing both integrity hashes and removing `run_id`, `created_at`, `source.received_at`, stage timestamps and stage durations. It is stable when source, effective options, stage outputs, model identity and environment are unchanged.
- `chain_verified`: true only after every stage input reference resolves to an existing source or stage output reference.

A false or unresolved chain prevents manifest emission.

## Dependency graph

The manifest stores stages in execution order, but integrity is verified as a dependency graph:

- Validation consumes `source.sha256`.
- Quality consumes the validation stage's `normalised_dataset` output.
- Forecast consumes the artefact it actually used. It may consume the validation stage's `normalised_dataset` output or a later routing artefact when that exists.

Quality and forecast may therefore reference the same validation output. A strict previous-array-element rule is not used.

## Client-data boundary

The manifest contains hashes, counts, options, outcome codes and environment facts. It contains no SKU identifiers, demand values, descriptions, customer names or site identifiers.

The source filename is the only client-controlled string allowed. Before emission, the serialised manifest is scanned against every source SKU identifier. Any match fails the run.

The client-facing statement is: `We keep the proof, not the data.`

## Model identity for production

Production remains on managed BigQuery TimesFM 2.5.

Required recorded values:

- Family: `TimesFM`.
- Version: `2.5`.
- Checkpoint: `provider_managed_not_exposed`.
- Provider: `BigQuery AI.FORECAST`.
- Context window: explicitly pinned to `512` in the query and manifest.
- Context points actually supplied: minimum, median and maximum by series.
- Horizon: effective requested horizon.
- Confidence level: `0.9`.
- Interval bounds: `[0.05, 0.95]` for the requested 90 percent interval.
- Backend and precision: `provider_managed_not_exposed`.
- Preprocessing: only behaviour documented or explicitly applied by Silurian. Provider internals are not inferred.
- Included and excluded series counts, with exclusion-reason counts.

The manifest states that Google manages the underlying weights and does not expose a revision hash through the service interface. This is a limitation, not a placeholder. Every forecast run also executes a fixed synthetic reference canary through the same provider path and records the input, current output and baseline output hashes. A changed output produces `drift_detected`.

## Effective options

Every stage records every effective option, including defaults. Options contain only values actually used. A missing user choice is represented by its applied default and source, not by omission.

The quality stage reuses the Story 1.2 options and thresholds. The forecast stage records horizon, context window, confidence level, provider model request and exclusion rules.

## Determinism measurement

Validation and quality remain bitwise reproducible.

Forecast determinism is measured on the deployed BigQuery path using ten identical runs over the same normalised input, options and deployment. The comparison covers every forecasted point and records:

- Run count.
- Confirmation from every job that the provider cache was not used.
- Maximum absolute difference.
- Maximum percentage difference. Reference values of zero are excluded from that percentage, compared by absolute difference and counted separately.
- Environment and model identity.
- Measurement timestamp.

Identical outputs across all ten runs permit `bitwise` for that measured environment. Any difference produces `tolerant` with the measured maximum percentage plus a documented safety margin. The evidence is recorded in `docs/1.3-determinism.md`.

Every measurement query sets `use_query_cache` to false, records `bigquery_use_query_cache: false`, and verifies `cacheHit` is false in the returned job metadata. A measured class is invalid without this evidence.

## Environment

The deployment supplies:

- Application version.
- Git commit SHA.
- Python runtime version.
- Numerically relevant library versions.
- BigQuery region.
- Container image digest where available.

Missing environment facts are represented as `not_exposed` only where the schema permits and the limitation is true. `REPLACE_WITH_ACTUAL`, dummy SHAs and friendly guesses are prohibited.

## Surfaces

The browser shows a compact provenance panel containing run ID, source filename, source hash prefix, analysis date and source, model and managed-provider identity, manifest hash prefix and the reproducibility statement.

The full manifest is downloadable as JSON. Printable quality and forecast reports include the run ID and manifest hash in the footer.

## Acceptance

1. Every emitted manifest conforms to the revised schema.
2. Valid dependency graphs verify; corrupted or unresolved references fail closed.
3. Raw source, normalised dataset, quality result and forecast result hashes are deterministic.
4. Exact manifest hashes distinguish separate runs.
5. Content fingerprints remain stable when only run identity and timing change.
6. No source SKU identifier appears in the serialised manifest.
7. No placeholder string or dummy commit reaches an emitted manifest.
8. Every effective option, including defaults, is present.
9. Forecast determinism is measured over ten uncached deployed runs, verified from job metadata and documented.
10. Quality and forecast exports carry the run ID and manifest hash.
11. The supplied portfolio produces the expected structure, allowing real deployment facts and timestamps.
12. Rejected validation produces a schema-valid validation-only manifest.
13. The synthetic reference canary records a baseline, matches it normally, and reports `drift_detected` when the stored baseline is deliberately altered.
