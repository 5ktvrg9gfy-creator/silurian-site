# Story 1.3 open questions

Status: the four Phase 1 contract decisions were approved. No design question blocks Phase 2.

## Q1. How should a managed BigQuery model satisfy checkpoint identity?

Decision: remain on managed BigQuery TimesFM 2.5. Record `provider_managed_not_exposed` for checkpoint, backend and precision, and state the service limitation plainly. Do not invent a revision or substitute the local Hugging Face identity.

Reason: the production service exposes the model family and version but not the weights revision. Self-hosting solely to obtain a checkpoint would materially increase operational scope.

## Q2. How should context length be recorded?

Decision: explicitly set `context_window => 512` in the BigQuery query and record 512 in the forecast stage.

Reason: the current automatic selection varies with input length and cannot be reconstructed from the friendly model name alone.

## Q3. How should exact run identity and timestamp-independent stability coexist?

Decision: retain `manifest_sha256` for the exact run and add `content_fingerprint_sha256` for a timestamp-independent reproducibility fingerprint.

Reason: the supplied golden algorithm includes timestamps, so one hash cannot be both unique per run and unchanged when timestamps move.

## Q4. What constitutes a run?

Decision: one user action is one run, and the manifest contains only stages that actually executed. Validate, assess quality and forecast actions therefore produce different valid stage sets. A later quality-routed portfolio forecast may contain all three stages.

Reason: this records reality, supports rejected runs and avoids claiming that an unused stage contributed to an output.
