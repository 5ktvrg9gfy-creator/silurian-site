# Story 1.3 Phase 0 survey

## Existing provenance

Story 1.1 already records the raw source SHA-256, effective validation options, findings, row counts, detected encoding and delimiter, normalised rows and validation metadata. Story 1.2 records the analysis date and source, inferred or overridden grain, thresholds, weighting, structural metrics, findings and quality bands.

These records are currently independent. Neither record contains a content reference to the artefact it consumed, and no object proves that a quality result came from a particular normalised dataset.

The forecast result records a provider name and output values but does not record the provider configuration, effective context window, model service identity, environment or reproducibility position.

## Production forecast path

Production uses `BigQueryTimesFMProvider` when `FORECAST_PROVIDER=bigquery_timesfm`. The query calls BigQuery `AI.FORECAST` with:

- Model: `TimesFM 2.5`.
- Horizon: supplied by the run.
- Confidence level: `0.9`.
- Context window: currently omitted, so BigQuery selects it automatically.
- Input type: `DATE` and `FLOAT64` arrays.
- Region: the configured `BIGQUERY_LOCATION`, defaulting to `US`.

BigQuery exposes the managed model family and friendly version but does not expose a weights revision, backend precision or checkpoint hash. Story 1.3 must record that limitation honestly. It must not manufacture a revision.

The local container provider is separate. It loads `google/timesfm-2.5-200m-pytorch`, uses a maximum context of 1024 and compiles the model locally. Its identity must not be written into a manifest for a BigQuery run.

## Current boundaries

The application has three user actions:

- Validate: story 1.1 only.
- Assess quality: stories 1.1 and 1.2.
- Forecast: story 1.1 plus the forecast stage.

A later portfolio forecast routed by quality may contain validation, quality and forecast in one run. Story 1.3 must represent only stages that actually ran.

Rejected validation still produces a manifest containing the source and validation stage. Quality and forecast stages are absent because they did not execute.

## Missing capabilities

1. Canonical JSON and artefact hashing shared by every stage.
2. A run context containing immutable timestamps, analysis date, source facts and effective options.
3. Stage records with input and output references.
4. Dependency-graph verification. Quality and forecast may both consume the validation output, so the chain is not necessarily linear.
5. Managed model identity and an explicit provider limitation statement.
6. Measured forecast determinism on the deployed BigQuery path.
7. Runtime metadata supplied by deployment rather than guessed in application code.
8. A compact provenance panel, full manifest download and export footer.
9. A no-client-data assertion over the serialised manifest.

## Supplied package verification

`20_portfolio_mixed.csv` contains 324 rows across 12 SKUs and is 8,210 bytes. Its source SHA-256 matches the golden manifest:

`558784ec94a1ddb59b8736e3b03fd2e741162db959f4da43628063422716f4d9`

The golden manifest hash also recalculates exactly when `integrity.manifest_sha256` is set to an empty string before canonicalisation.

## Contract friction resolved before Phase 2

The supplied golden manifest includes timestamps in `manifest_sha256`. That hash must therefore change for every run. The acceptance requirement also asks for a stable value when only timestamps change. One field cannot provide both properties.

The approved resolution is to keep `manifest_sha256` as the exact identity of one manifest and add `content_fingerprint_sha256`, calculated without run identity and timestamp fields. The schema and golden comparison will be updated accordingly.
