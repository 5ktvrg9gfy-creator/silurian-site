# Story 1.4 open questions

Status: the implementation questions are closed. The decisions below are authoritative alongside `1.4-contract.md` and the current schemas.

## Q1. What does the content fingerprint exclude?

Decision: exclude run identity, all timings, the readable or hashed filename, extension, application version, Git commit and container identity. Retain the source byte hash, effective options, stage outputs, model identity, calculation libraries and region.

Reason: deployment-only identity must not prevent two calculation-equivalent runs from sharing a fingerprint.

## Q2. In what order are the two manifest hashes calculated?

Decision: clear both integrity fields and calculate the content fingerprint over the stripped manifest. Write the real fingerprint back. Then clear only `manifest_sha256` and calculate the exact manifest hash over the manifest containing the real fingerprint.

Reason: the exact hash must cover the fingerprint. Clearing both fields for the final hash would let the fingerprint change without moving the manifest hash.

## Q3. Which stages appear in a run?

Decision: only stages that executed appear. A quality run does not invent a forecast stage. A rejected validation run contains validation only.

Reason: provenance records what produced the result, not a desired future pipeline.

## Q4. What is the independent golden boundary?

Decision: structure, timings and hashes are generated by the real engine. Metrics, bands and expected findings must still match the unchanged expectation file. Do not regenerate the expectation file from the engine under test.

Reason: a golden copied from the current engine cannot independently detect a calculation defect.

## Q5. What happens when forecast determinism is unknown?

Decision: reproduction returns `not_comparable` and states that the forecast cannot be verified. It must not report a tolerant or exact match without measured evidence.

Reason: failure to measure reproducibility is not evidence of reproducibility.
