# Story 1.5 data map

Status: Phase 0 approved, Phase 1 basis

Version: 0.2

Audit date: 2026-08-30

Scope: Silurian Forecast Diagnostic deployed on Vercel, with forecasting through Google BigQuery `AI.FORECAST`

## Purpose and boundary

This document records what the implementation does today. It is not the public data handling statement and it does not make contractual or GDPR role determinations. Items marked `NEEDS CHECK` or `GAP` cannot support a client-facing claim until they are verified or corrected.

Demand history, SKU identifiers, quantities, dates, inventory inputs, validation examples, quality findings and forecast outputs are treated as client data whether or not they are personal data. Masked SKU codes with real volumes are pseudonymised, not anonymised.

The role descriptions below are working positions for system design:

- The client controls the source data and the purpose for which it is supplied.
- Silurian operates the diagnostic and controls its Vercel and Google Cloud accounts.
- Vercel processes uploads and responses as the hosting provider.
- Google processes forecast inputs and results as the BigQuery provider.
- If personal data is present, the legal controller, processor and sub-processor roles require qualified review before they are stated in a contract, DPA or client answer.

## Executive finding

The application has no database or object store and does not deliberately retain uploads, results, bundles or manifests server side. That narrow statement is supported by the code. A broader statement that client data is not retained is not yet supported.

Three current facts prevent that broader claim:

1. FastAPI receives each multipart upload through a spooled temporary file, which can move from memory to the function filesystem before the application reads it.
2. BigQuery writes query results to an anonymous temporary table for up to 24 hours even when reuse of cached results is disabled. BigQuery also retains job metadata for six months.
3. Vercel retains runtime logs according to the account plan and publishes a broader platform backup position. The current plan, enabled log drains, project region and applicability of those backups to function request data have not been verified from the project settings.

The manifest and bundle split remains useful. Phase 1 removes the client-supplied source filename from newly emitted manifests and replaces it with a filename SHA-256 plus extension. Legacy 1.2 manifests remain compatible and can contain a readable filename, so claims about client-data-free proof apply to version 1.3 and later.

## End-to-end flow

```text
Client device
  -> browser File object and form fields
  -> HTTPS request through Vercel firewall, edge and function routing
  -> FastAPI multipart spool and Python request memory
  -> validation and quality in Python memory
  -> forecast only: date and demand arrays sent to BigQuery AI.FORECAST
  -> BigQuery anonymous result table and job metadata
  -> JSON response through Vercel to browser memory
  -> optional client-side downloads on the client's device
```

There is no application database, blob store, message queue, server-side session store or application-managed backup in this path.

## Detailed location map

### 1. Browser before upload

**Status:** `VERIFIED IN CODE`

- **Data and form:** The complete selected CSV exists as a browser `File` object. Form fields can also contain inventory, inbound supply, safety stock, product or market text, lifecycle stage, planning adjustments and dates.
- **Retention:** The page keeps the selected file until the user replaces it, resets the form, reloads, closes the tab or the browser releases it. The browser and operating system may retain their own recent-file or download history.
- **Storage controls:** The diagnostic has no `localStorage`, `sessionStorage`, IndexedDB, cookie, service worker or client-side analytics code. It does not copy the upload into a browser database or cache.
- **Technical control:** The client controls the device and browser. Silurian supplies the page code.
- **Working role position:** Client-controlled source. No separate sub-processor is introduced by application code at this point. The browser vendor and device services remain within the client's environment.
- **Destruction:** The application relies on browser lifecycle and user action. It cannot erase the original source file from the client device.
- **Evidence:** `static/index.html` file inputs and `FormData` submissions; repository search for browser storage, cookies, service workers and external scripts.

### 2. Browser results and downloads

**Status:** `VERIFIED IN CODE`, manifest gap closed in Phase 1

- **Data and form:** Validation and quality responses contain client identifiers, finding examples and metrics. Forecast responses contain forecasts and planning outputs. The confidential run bundle contains client data by design. The quality JSON and validation record can also contain client data. A version 1.3 manifest contains hashes, counts and settings, including a filename hash and extension but no readable filename.
- **Retention:** JavaScript variables hold the latest quality report, manifest and bundle until page reload or tab closure. Download actions create a `Blob`, trigger a local download and revoke the object URL immediately. Downloaded files persist on the client device and may enter client backup or sync systems.
- **Technical control:** The client controls downloaded outputs. Silurian controls the response shape and download code.
- **Working role position:** Client controls its downloaded evidence. No server-side handoff or Silurian archive exists.
- **Destruction:** Browser memory is released by browser lifecycle. The client deletes downloaded files under its own policy.
- **Evidence:** `static/index.html` functions `downloadBundle`, `downloadManifest`, validation-record download and quality download; `run_bundle.py`.
- **Compatibility note:** Legacy 1.2 manifests retain the readable filename and are labelled by schema version. New 1.3 manifests emit `filename_sha256` and `extension` instead.

### 3. Transport and Vercel edge

**Status:** `LONDON PIN IMPLEMENTED`, deployment and account settings `NEEDS CHECK`

- **Data and form:** The complete multipart request body and form fields cross the network to Vercel. JSON results cross back to the browser. Vercel's firewall, edge and function routing necessarily see request metadata and route the body to the function.
- **Protection:** Vercel documents HTTPS with TLS 1.3 in transit and AES-256 for data at rest. Vercel terminates the client connection, so this is transport encryption rather than client-to-BigQuery end-to-end encryption.
- **Retention:** The repository does not define a Vercel request-body store. Vercel runtime logs retain request metadata according to plan. Whether any platform control retains request bodies is not established by the repository or the public runtime-log page.
- **Technical control:** Silurian controls the Vercel project. Vercel controls the hosting, firewall, routing and function platform.
- **Working role position:** Vercel is the hosting provider and likely a sub-processor when Silurian is acting as processor. This requires contractual review.
- **Destruction:** No application action can delete data in Vercel's transient network path. Platform retention and deletion follow Vercel controls and terms.
- **Evidence:** Vercel security documentation states TLS 1.3 and AES-256; Vercel firewall documentation states that every incoming request passes platform firewall layers; `forecast-app/vercel.json` routes all requests to `app.py`.
- **Phase 1 control:** `vercel.json` pins the function to London `lhr1` and configures no failover region. This chooses UK processing over automatic cross-region failover.
- **Needs check:** Confirm the effective preview region, Vercel plan, log drains, Observability Plus, Web Analytics, Speed Insights and any project-level monitoring integration in the project dashboard.

### 4. Multipart temporary file

**Status:** `VERIFIED FRAMEWORK BEHAVIOUR`, with a `GAP`

- **Data and form:** The complete uploaded CSV or JSON bundle is placed in FastAPI/Starlette's `UploadFile`, backed by a Python `SpooledTemporaryFile`. It starts in memory and can roll to the runtime filesystem above the framework's spool threshold.
- **Retention:** It exists for the request and should be closed during request cleanup. The application does not explicitly close or wipe it and does not verify platform deletion after the invocation.
- **Technical control:** Silurian selects FastAPI and Starlette. Vercel controls the runtime filesystem and instance lifecycle.
- **Working role position:** Vercel is the relevant hosting provider for any disk-backed spool.
- **Destruction:** Framework close and serverless lifecycle, not an application deletion control. Memory and temporary disk are not cryptographically wiped by the application.
- **Evidence:** Every upload endpoint declares `UploadFile` and calls `await file.read()` in `app.py`. FastAPI documents `UploadFile.file` as a `SpooledTemporaryFile` which moves to disk above a size limit.
- **Gap:** The 4 MB application check happens after multipart parsing and after `await file.read()`. It prevents later processing, but it does not prevent the framework from spooling the incoming body. Technical conformance must either accept and describe this bounded temporary file or replace the upload path with one whose cleanup can be explicitly verified.

### 5. Application memory

**Status:** `VERIFIED IN CODE`

- **Data and form:** Raw bytes, parsed rows, normalised rows, SKU values, finding examples, quality metrics, forecast inputs and outputs, manifests and bundles exist as Python objects. Planning context fields exist in request memory for single-SKU forecasts.
- **Retention:** Objects live for the request. The module-level `_provider` can outlive a request, but it stores the provider object rather than client histories or results. No client result is assigned to global state.
- **Technical control:** Silurian controls application code. Vercel controls process memory and function reuse.
- **Working role position:** Silurian operates the processing; Vercel supplies the runtime.
- **Destruction:** Python reference release, garbage collection and function lifecycle. There is no explicit memory zeroisation and no guarantee of immediate physical erasure.
- **Evidence:** `app.py`, `validator.py`, `quality_engine.py`, `forecast_engine.py`, `run_manifest.py` and `run_bundle.py`.

### 6. Validation and quality path

**Status:** `VERIFIED IN CODE`

- **Data and form:** Validation and quality use the source and normalised rows entirely in the function process. Quality consumes the `ValidationResult` rather than saving and reloading a dataset.
- **Retention:** Request lifetime only, except data returned to the browser.
- **External processing:** These stages do not call Google BigQuery or another model provider.
- **Destruction:** Same application-memory and multipart-spool lifecycle as above.
- **Evidence:** `/api/validate` and `/api/quality` in `app.py`; `docs/1.2-survey.md`.

### 7. BigQuery forecast input

**Status:** `VERIFIED IN CODE`, production deployment pending

- **Data and form:** Each forecast call sends two array query parameters: observed dates and demand values. SKU, customer, site, source filename, descriptions, inventory, receipts, safety stock and planning-adjustment text are not sent to BigQuery by this connector. A fixed synthetic canary is sent separately for model identity checks.
- **Query:** A parameterised SQL query builds an in-query `input` CTE and calls `AI.FORECAST`. The application does not upload a source file and does not create a named dataset or named input table.
- **Cache control:** Every call sets `use_query_cache=False`. Phase 1 now stops every forecast if the completed job unexpectedly reports `job.cache_hit=true`, including ordinary production runs and not only the determinism measurement.
- **Region:** Every query passes `location=self._location`; the code default is `europe-west2`, which Google identifies as London. Story 1.4 production evidence recorded the configured region as London, but the environment value should be rechecked as part of deployment acceptance.
- **Technical control:** Silurian controls the Google Cloud project, service account and query configuration. Google controls BigQuery and the managed TimesFM service.
- **Working role position:** Google is a forecasting sub-processor when Silurian is acting as processor. This requires contractual review and an approved sub-processor position.
- **Evidence:** `bigquery_timesfm.py`; `determinism.py`; `run_manifest.py`; Google BigQuery location documentation.
- **Deployment check:** Confirm the assertion against an authenticated preview forecast and inspect its job metadata.

### 8. BigQuery result table and cache

**Status:** `APPROVED PROVIDER LIFECYCLE`

- **Data and form:** Forecast values and provider status are query results. BigQuery writes query results to a randomly named temporary table in a hidden anonymous dataset when no named destination table is supplied.
- **Retention:** Google documents that the temporary result table can exist for up to 24 hours. Setting `use_query_cache=false` prevents reuse of an existing cached result, but it does not mean that no result table is created.
- **Access:** Google states that access to the anonymous temporary result is restricted to the user or service account that created the query job. Silurian Google Cloud administrators may still be able to inspect jobs and related resources under project permissions.
- **Region and protection:** The query explicitly runs in London. Google documents default encryption of BigQuery content at rest and encryption in transit.
- **Destruction:** Current code performs no explicit deletion. Google documentation says anonymous temporary tables are not visible through standard table listing and manipulation methods. They expire under the provider's temporary-table lifecycle within 24 hours.
- **Evidence:** `bigquery_timesfm.py` does not set a destination table and has no dataset or table deletion call; Google cached-results and writing-results documentation.
- **Approved position:** Silurian creates no named dataset or table. Creating a named per-run destination solely to delete it would increase exposure and add a persistence failure mode. The later written statement must state the anonymous-table access restriction and the provider's retention window explicitly. It must not make an unqualified no-retention claim.

### 9. BigQuery job history and audit logs

**Status:** `PARTLY VERIFIED`, parameter exposure `NEEDS CHECK`

- **Data and form:** BigQuery creates a query job containing identity, location, status, timings, query text, resource use, cache status and destination metadata. The SQL text contains parameter names rather than embedded demand values. BigQuery audit logs can contain SQL text, resource identifiers, caller identity and IP information.
- **Retention:** Google documents six months of BigQuery job history. The `INFORMATION_SCHEMA.JOBS` view exposes job metadata for 180 days. Audit-log retention depends on Google Cloud Logging configuration and any configured sinks.
- **Technical control:** Silurian controls project IAM, Cloud Logging configuration and sinks. Google operates the service.
- **Working role position:** Google is the service provider. People with relevant Google Cloud permissions can inspect job history or audit logs.
- **Destruction:** Current application code does not delete job metadata or audit logs. Provider and project retention controls apply.
- **Evidence:** Google BigQuery job-management, `INFORMATION_SCHEMA.JOBS` and audit-log documentation.
- **Needs check:** Run one authenticated forecast, inspect the job resource and Cloud Audit Log, and determine whether the array query parameter values are retrievable. Also inspect log buckets, retention, sinks and IAM. Until that is done, do not claim that BigQuery retains metadata only and never retains demand values beyond the temporary result.

### 10. Application and platform logs

**Status:** `LOCAL REGRESSION VERIFIED`, live Vercel inspection outstanding

- **Data and form:** Application code writes fixed error messages without exception text or tracebacks. It does not deliberately log raw uploads, normalised rows, findings, bundles, manifests or SKU values.
- **Client-facing errors:** Several expected errors return `detail=str(exc)`. Some forecast and reproduction errors can contain a SKU identifier. These are returned to the requesting client, not deliberately written by application logging, but platform behaviour on failed requests must be tested.
- **Platform metadata:** Vercel runtime logs include request path, method, status, domain, request ID and function details. The public Vercel page does not state that request bodies are included by default.
- **Retention:** Vercel documents current runtime-log retention by plan: one hour on Hobby, one day on Pro, three days on Enterprise, or up to 30 days with Observability Plus. The active plan is not verified.
- **Technical control:** Silurian project members control access to the Vercel dashboard and any log drains. Vercel operates the log service. Any configured drain or error-monitoring vendor would become another recipient.
- **Destruction:** Platform expiry, plus any separate drain retention. There is no application deletion API for Vercel logs.
- **Evidence:** `app.py`; repository search found no Sentry, error-monitoring SDK or log drain configuration; Vercel runtime-log documentation.
- **Evidence completed locally:** A full quality run and a deliberately triggered unexpected portfolio error assert that no fixture SKU appears in captured application logs, including when the exception message itself contains a fixture SKU.
- **Gap:** Deploy the preview, repeat the success and error paths, and inspect the actual Vercel entries. Verify project members, plan, log drains and monitoring integrations. Local capture does not satisfy the provider-side part of acceptance item 7.

### 11. Analytics and cookies

**Status:** `VERIFIED IN REPOSITORY`, platform settings `NEEDS CHECK`

- **Data and form:** No client-side analytics, advertising scripts, trackers, external fonts or application cookies are present in the diagnostic. No server-side analytics SDK is installed.
- **Platform telemetry:** Vercel necessarily records operational request events. Whether Vercel Web Analytics, Speed Insights or an account-level integration is enabled cannot be determined from this repository.
- **Retention and destruction:** None in application code. Any enabled platform feature follows its own configuration and retention.
- **Evidence:** `static/index.html`, `requirements.txt`, `vercel.json` and repository search.
- **Needs check:** Confirm project integrations and dashboard settings before repeating the marketing-site statement for the diagnostic.

### 12. Outputs, manifest and bundle

**Status:** `VERIFIED IN CODE`, version 1.3 filename control implemented

- **Validation record:** Contains finding examples and raw values needed to explain the decision. It is returned to the browser and can be downloaded. It contains client data.
- **Quality output:** Contains SKU identifiers, metrics, findings and exceptions. It is returned to the browser and can be downloaded. It contains client data.
- **Run bundle:** Contains recorded results, SKU-level evidence, findings and forecasts. It is marked confidential, returned to the browser and not stored by application code. Reopening reads a client-supplied bundle into request memory and returns it without recomputing.
- **Run manifest:** Contains source hash, byte and row counts, stage hashes, settings, model evidence, environment and timings. Version 1.3 excludes readable SKU, demand and filename values. It retains `filename_sha256` and `extension` so a client can check a filename locally without revealing it. Legacy version 1.2 can contain a readable filename.
- **Retention:** No server-side output store. Browser and client filesystem retention apply.
- **Technical control:** Silurian controls formats; the client controls downloaded copies.
- **Destruction:** Response and application memory lifecycle server side; client policy for downloaded files.
- **Evidence:** `run_bundle.py`, `run_manifest.py`, schemas and `static/index.html`.

### 13. Reopening a recorded bundle

**Status:** `BROWSER-ONLY IMPLEMENTED`, deployment pending

- **Data and form:** The browser reads the selected JSON bundle locally, verifies the bundle SHA-256 and embedded manifest SHA-256 with Web Crypto, checks the recorded stages, and renders the recorded results. It makes no network request.
- **Retention:** Browser memory and client-device retention only. Vercel, application memory and the multipart spool do not receive a reopened bundle.
- **Technical control:** Silurian controls both the bundle format and the browser code. No model or external data service is needed to reopen it.
- **Working role position:** The client remains the only party handling the bundle during reopen.
- **Destruction:** Browser lifecycle and client action.
- **Evidence:** The server reopen endpoint has been removed. A headless-browser test reopened the canonical golden bundle, rendered its recorded contents and observed zero requests after page load.

### 14. Backups and replicas

**Status:** `NO APPLICATION BACKUP`, provider scope `NEEDS CHECK`

- **Application-managed backups:** None. There is no persistent application data store to back up.
- **Vercel:** Vercel publishes a general security statement that customer data is backed up every two hours, retained for 30 days and globally replicated. Public documentation reviewed for this audit does not define whether transient function request bodies, temporary runtime files or only persistent platform account data fall within that statement.
- **BigQuery:** Google stores temporary query results and job metadata under BigQuery's managed storage and resiliency controls. BigQuery data in a selected single region is stored redundantly across zones in that region. Google states that backups remain encrypted, but the application has no control over provider backup copies of managed transient data.
- **Client device:** Downloaded outputs may be included in client endpoint, cloud-drive or enterprise backups.
- **Technical control:** Vercel and Google control their provider backup systems; the client controls its own backups.
- **Destruction:** Provider lifecycle and contractual deletion controls. No Silurian application API currently proves deletion from provider backups.
- **Needs check:** Obtain a precise Vercel answer for function uploads and temporary filesystem data, and review the applicable Vercel and Google contractual terms before describing backup retention to a client.

## Current controls that can support later statements

- No application database, blob store or server-side session store.
- No deliberate server-side save of uploads, results, manifests or bundles.
- Validation and quality run without an external model provider.
- BigQuery receives only the dates and demand values required for a forecast, not SKU or commercial context fields.
- BigQuery jobs explicitly request the London location.
- Query result reuse is disabled in every connector call.
- The browser has no application storage, service worker, analytics script or non-essential cookie code.
- The browser creates downloads locally and immediately revokes temporary object URLs.
- Google credentials are not sent to the browser. The function uses a short-lived Vercel OIDC token to impersonate the configured service account.
- Application code does not deliberately log datasets, rows, findings, bundles or SKU values.

## Data-minimisation assets to lead with later

- BigQuery receives only anonymous numeric series: dates and demand values. It receives no SKU, customer, site, filename, description or commercial context.
- Reopening a confidential run bundle happens entirely in the client's browser and sends no request to Silurian or a provider.
- A version 1.3 manifest carries a filename hash rather than a readable filename and contains no source SKU or demand value.
