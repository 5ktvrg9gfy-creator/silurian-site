# Build brief: story 1.4, reproducible and re-openable runs

Silurian Forecast Diagnostic. Sprint 1, story 1.4. Follows 1.1, 1.2 and 1.3.

Same phases and question protocol. Two files ship with this brief: `run_bundle.schema.json` and `run_bundle.golden.json`, the latter generated entirely from the real mixed portfolio metrics with nothing invented.

---

## 1. What is left after 1.3

Story 1.3 delivered the proof. `content_fingerprint_sha256` already answers whether two runs are the same run, and the determinism measurement answers whether the forecast stage is stable.

What 1.3 does not do is let you **open** anything. The manifest proves what happened. It cannot show a client what they saw. Walking someone through a run a week later needs the findings, the per SKU table, the exceptions and the forecast, none of which are in the manifest and none of which are stored anywhere.

So 1.4 is three things:

1. A portable **run bundle** the client keeps, containing everything needed to re-render the run.
2. **Reopen**, which renders what was recorded and never recomputes.
3. **Reproduce**, an explicit action that re-runs the source and compares fingerprints.

---

## 2. The distinction that matters most in this story

**The manifest contains no client data. The bundle does.**

The manifest holds hashes, counts and options, which is what lets it be archived indefinitely by both sides under a no-retention position. The bundle holds SKU identifiers, demand metrics, findings and forecast values. It is the client's data in a file with your name on it.

Treating them the same is the failure mode. Someone will email a bundle the way they would email a manifest.

Therefore:

- The bundle carries a required `confidentiality` block with `contains_client_data: true` and a plain statement, at the top of the file, before anything else.
- The download UI says so at the point of download, not in a help page.
- The bundle is never stored server side, never logged, and never cached. It is generated, handed over, and forgotten.
- Filename convention makes it obvious, for example `silurian-run-<short id>-CONFIDENTIAL.json`.

Say the pairing plainly in the report: **the manifest is the proof and it is safe to keep anywhere, the bundle is the evidence and it belongs to the client.**

---

## 3. Reopen never recomputes

The trap in this story, and it is a serious one.

A bundle exported under quality engine 1.0.0 is reopened when the deployed engine is 1.2.0, with a changed threshold. If reopening re-renders by recomputation, the client sees different numbers from the ones they were given, with no explanation, in a meeting.

**Rule: reopening renders exactly what was recorded in the bundle, read only.** No recomputation, no re-banding, no re-rendering of messages from current templates. The bundle is a photograph.

When the deployed engine versions differ from those in the bundle, the view says so calmly and factually: this run was produced by quality engine 1.0.0, the current engine is 1.2.0, and the results shown are as originally produced. Offer the reproduce action from there, as a separate deliberate step.

Refuse to import a bundle whose `bundle_schema_version` the application does not recognise. Partial reads are worse than a refusal.

---

## 4. Reproduce, as an explicit action

The client-facing feature this story is really for. Give it the source file and a bundle, and it answers whether the same input still produces the same result.

Outcomes, and each needs different words:

| Outcome | Meaning |
|---|---|
| `reproduced` | Content fingerprints match exactly. Everything is identical |
| `reproduced_within_tolerance` | Validation and quality match exactly, the forecast differs within the measured tolerance from 1.3 |
| `differs` | Same engine versions and options, different results. This is a defect and should be treated as one |
| `not_comparable` | Engine versions, options or environment differ, so this is a new run rather than a failed reproduction |

Two rules that keep this honest:

- **Validation and quality must match exactly.** They are pure functions. Any difference is a bug, never a tolerance.
- **The forecast is compared against the measured tolerance from story 1.3**, not against a convenient number. If `determinism.class` is still `unknown`, the reproduce action must say the forecast stage cannot be verified rather than quietly passing it.

`not_comparable` is the honest answer more often than it looks. Deploy a new quality engine and every older bundle becomes not comparable, which is correct: you are not reproducing the run, you are running a new one.

## 5. A correction to the 1.3 fingerprint, found by thinking about this story

`content_fingerprint_sha256` currently includes the whole `environment` block, including `app_version`, `git_commit` and `container_image_digest`. Those change on every deploy, including deploys that change nothing about the calculation.

The consequence is that no run reproduces across an unrelated deploy. Every comparison returns `not_comparable`, the feature becomes useless, and the reason will be hard to see from the outside.

**Fix the fingerprint scope.** Include what can change the output:

- source hash and all effective options
- every stage `engine_version`
- model identity: family, version, provider, checkpoint, context window, horizon, confidence level
- `key_libraries` and `region`

Exclude what cannot:

- `app_version`, `git_commit`, `container_image_digest`
- run id and every timestamp, as already specified

This is a change to story 1.3 output, so bump the manifest schema minor version and note it. It is much cheaper now than after bundles exist in the wild.

Raise a question if you disagree on `region`. I have kept it in because a different BigQuery region is a different deployment of the model and could legitimately produce different numbers.

## 6. Bundle contents

See `run_bundle.schema.json`. The shape:

- `bundle_schema_version`, refused if unknown
- `confidentiality`, required, as above
- `manifest`, the complete 1.3 manifest embedded verbatim and validated against the manifest schema on import
- `results`, one key per stage that actually ran: validation findings and passes, the full quality result with per SKU records, forecast series with intervals and excluded series with reasons
- `reproduction`, absent on export, populated only when a reproduce action has run
- `integrity`, with `bundle_sha256`, plus the manifest hash and fingerprint copied from inside

Integrity on import: verify `bundle_sha256`, then confirm `manifest_sha256` matches the embedded manifest's own value. That second check proves the manifest inside was not swapped for a different one. **A bundle that fails either check is refused, never repaired.** I have tested that a single altered field is detected.

---

## 7. The golden bundle

`run_bundle.golden.json`, 12 SKUs, 9 findings, 8 exceptions, generated from `expected_quality.json` so every metric in it is the value your quality engine must produce.

It is a **quality run**: validation and quality, no forecast stage. That is deliberate. Fabricating forecast numbers in a golden fixture would invite tests to assert against values I invented. The forecast section is specified in the schema and the shape is defined, but the golden does not pretend to know what TimesFM returns.

The finding text in it is written the way the report should read: detail, implication, action, in that order, with the implication doing the work. Use it as the copy target, not just the structure target.

## 8. Acceptance

1. Export a bundle from a completed run. It validates, and the embedded manifest validates against the manifest schema.
2. Import that bundle and render the full run read only, with no recomputation. Instrument this: assert no quality or validation engine call occurs during a reopen.
3. A bundle with any single altered field is refused on import.
4. A bundle with a swapped manifest is refused, caught by the manifest hash check.
5. An unknown `bundle_schema_version` is refused, not partially read.
6. Reopening a bundle whose engine versions differ from the deployed ones renders the recorded results and states the version difference.
7. Reproduce over an unchanged deployment returns `reproduced`.
8. Reproduce after a deliberate threshold change returns `not_comparable`, naming what differs.
9. Reproduce where validation or quality differ under identical versions and options fails the build. That is a determinism defect, not a tolerance case.
10. Reproduce while `determinism.class` is `unknown` reports that the forecast stage cannot be verified, rather than passing it.
11. The fingerprint is stable across a deploy that changes only `app_version`, `git_commit` and `container_image_digest`.
12. No bundle is written to server-side storage or logs. Assert on the log output.
13. Golden comparison: a quality run over `20_portfolio_mixed.csv` produces a bundle structurally identical to `run_bundle.golden.json`, with every metric matching.

---

## 9. Definition of done

- A run can be handed to a client as one file and reopened by them a week later, showing exactly what they saw.
- Reopening cannot silently change a number, and the code makes that structurally impossible rather than merely intended.
- Reproduce gives a plain answer with the evidence behind it, including the honest `not_comparable`.
- The confidentiality distinction between manifest and bundle is visible at every point a file leaves the application.
- The fingerprint reproduces across deploys that changed nothing that matters.
