# Build brief: story 1.5, written data handling position

Silurian Forecast Diagnostic. Sprint 1, story 1.5. The last story in sprint 1.

Same phases and question protocol. This story is different in kind from the previous four, so read section 1 before anything else.

---

## 1. This is not a writing story

The backlog describes 1.5 as a statement on the page. That is the last twenty percent of it.

**The order is: find out what actually happens to client data, change the system where the answer is wrong, then write a statement that describes the corrected reality.** Writing first produces a page that is aspirational, and an aspirational data handling statement is worse than none. A client's IT function will test it, and the first thing they test is whether it is true.

So this story has three parts:

1. A data flow audit. Every place client data exists, however briefly.
2. Technical conformance. Changes so the system matches the position you want to hold.
3. The written statement, for three audiences.

Nothing gets written until parts one and two are done.

**The scope caveat, stated once.** I can tell you what the system does and what claims that supports. I am not a lawyer, and neither of us should be drafting contractual or regulatory language. Anything that becomes a contractual commitment, a GDPR role assertion, a data processing agreement or a sub-processor list needs review by someone qualified. That is a commercial decision and it stops with James.

---

## 2. Phase 0: the data flow audit

Produce `docs/1.5-data-map.md`. For every point below, state what client data exists there, in what form, for how long, who controls it, and how it is destroyed.

Trace the whole path, not the parts you designed:

- **Browser.** The uploaded file before it leaves. Any use of localStorage, sessionStorage or IndexedDB. Anything held in a service worker cache.
- **Transport.** TLS, obviously, but also whether any intermediate proxy or edge function sees the body.
- **Application memory.** The parsed dataset during validation, quality and forecast.
- **Temporary files.** Anything written to disk by the runtime, including whatever the framework does with multipart uploads without being asked.
- **BigQuery.** The dataset and tables created for `AI.FORECAST`, the query results, the job history, and the query result cache. See section 3, this is where the real exposure is.
- **Logs.** Application logs, platform logs, and any error or performance monitoring. See section 3, this is the second real exposure.
- **Analytics.** Anything client side or server side that records events.
- **Outputs.** The run bundle from story 1.4, which contains client data by design, and the run manifest, which does not.
- **Backups.** Anything the platform does automatically that you did not configure.

For each: **who is the controller, who is the processor, and who is a sub-processor.** Google is a sub-processor the moment `AI.FORECAST` runs, and that fact belongs in the statement whether or not anyone asks.

Stop after the map and wait. The map determines the rest of the story.

---

## 3. Two exposures I can already name

Both were found while building 1.3 and 1.4. Check them first because they are the ones most likely to make a written claim untrue.

### 3.1 The BigQuery query result cache

BigQuery caches query results in a temporary table by default, and that cache persists for hours after the run. A statement saying data is not retained is inaccurate while it is on.

This is the same setting that would have invalidated the 1.3 determinism measurement, and it needs disabling for a second and more important reason here. Disable it for every production forecast run, not only for measurement runs, and confirm from job metadata rather than trusting the flag.

Also audit: the dataset and tables created for a run, their expiry, and whether they are explicitly deleted at the end of a run or left to a default expiry. Explicit deletion, with a short default expiry as a backstop for crashed runs, is the position that survives a security review. Job history retains metadata regardless, and the statement should say so rather than pretend otherwise.

### 3.2 Client data in logs and error reporting

This one is easy to miss and it is the more likely leak.

Story 1.1 findings deliberately carry example rows with raw values, because naming the row is what makes a message useful. If a finding is ever logged, attached to an exception, or sent to an error monitoring service, those raw values leave the application and land in a third party system with its own retention.

Required:

- Findings and normalised rows never enter logs. Log codes, counts and the run id, never values.
- Exception handlers must not attach the dataset, the findings, or any row to the error context. Check what the framework attaches by default, which is usually more than you expect.
- If any error monitoring is connected, configure scrubbing and then verify it by triggering a real error with a real fixture and reading what arrived.
- A test asserts that a full run over `20_portfolio_mixed.csv` produces no SKU identifier in any log output. Same assertion style as the manifest test in 1.3, which already works.

## 4. Technical conformance

Decisions for James, with my reasoning. These are commercial choices, not technical ones, so they stop with him.

**Region.** Set the BigQuery location to a UK or EU region rather than the `US` default. Cost now is one configuration value. Cost later is explaining to a pharma client's security reviewer why their demand data crossed the Atlantic, after they have already sent it. The reasoning is commercial, the decision is yours.

**Deletion.** Explicit deletion of any dataset or table created for a run, plus a short expiry as a backstop. Verified by a test that creates a run and then confirms the objects are gone.

**Retention default.** No server-side storage of uploads, results, bundles or manifests. Story 1.4 already made the bundle the client's file rather than yours, which is what allows this claim to be simple.

**Anonymisation language.** The site currently asks for anonymised data. Two problems. First, clients will send real SKU codes regardless of what the page asks, so the statement must describe what happens to real identifiers, not the ideal case. Second, masked SKU codes with real volumes are pseudonymised, not anonymised, and using the wrong word in front of a data protection officer costs credibility instantly. Say pseudonymised, or avoid the term and describe what the helper actually does.

## 5. The written statement

Three audiences, three lengths, one set of facts. Every claim traceable to a control in the data map.

**One, the page.** Four or five sentences beside the upload control, in plain English, for a supply chain manager who is about to hand over data and wants to know if that is sensible. What happens to the file, how long it exists, who else touches it, what you keep.

**Two, a data handling note.** One page, for a client's IT or security function. The data map in readable form: flow, sub-processors, region, retention and deletion, logging position, encryption in transit and at rest, and what is explicitly not done. Include the manifest and bundle distinction, because it is unusual and it is a strength: the proof carries no client data and the evidence belongs to the client.

**Three, the question set.** `client-security-questions.md` ships with this brief. It carries the questions a pharma client's security and procurement functions actually ask, with where each answer comes from. Fill it in once and it is reusable across engagements. Expect it to shorten a security review from weeks to days, which matters more than it sounds when a fixed-fee engagement is ten working days long.

### What must never be claimed

- Not GDPR compliant. Compliance is a property of an organisation assessed against a purpose, not a badge a tool wears.
- Not anonymised, where pseudonymised is the truth.
- No certification you do not hold. No ISO 27001, no SOC 2, no implication of either through layout or wording.
- Not "we never see your data", if the application processes it.
- No claim that Google does not process the data, because `AI.FORECAST` means Google does.

Understating is safe. Every overstatement is discoverable by someone whose job is to discover it.

## 6. Acceptance

1. `docs/1.5-data-map.md` covers every location in section 2, with retention and destruction for each.
2. Every sentence in the written statement maps to a line in the data map. A claim with no control behind it is removed, not softened.
3. BigQuery query cache disabled in production, verified from job metadata.
4. Run datasets and tables explicitly deleted, verified by a test that checks they are gone.
5. Region set as decided, and recorded in the manifest, which already carries the field.
6. No SKU identifier from `20_portfolio_mixed.csv` appears in any log or error output during a full run, asserted by test.
7. Error monitoring, if connected, verified by triggering a real error and reading what arrived, not by reading the configuration.
8. The three written surfaces exist, agree with each other, and agree with the map.
9. The statement is dated and versioned, so a client can tell which version they were shown.
10. No prohibited claim from section 5 appears anywhere, including in marketing copy on the site.

---

## 7. Definition of done

- Someone hostile could read the statement, audit the system, and find no gap between them.
- A security questionnaire can be answered from prepared material rather than improvised.
- Nothing in the statement depends on a promise about future behaviour.
- The legal and contractual questions are identified and flagged for qualified review rather than answered by any of us.

---

## 8. What this closes, and one thing it opens

Sprint 1 ends here. The tool takes a client file, refuses it honestly when it must, describes the state of the data, proves what produced every number, hands the client a re-openable record, and can explain what happened to their data.

The thing it opens: the data handling note and the question set are consulting assets in their own right, independent of the tool. Most small consultancies cannot answer a pharma security questionnaire at all. Having the answers ready is a differentiator during procurement, and it is worth keeping them current as the product changes rather than rewriting them under time pressure during a live engagement.
