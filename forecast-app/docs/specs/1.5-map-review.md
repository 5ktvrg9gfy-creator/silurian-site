# Review of the story 1.5 data map, version 0.1

**Recommendation: approve as the basis for Phase 1, with one gap withdrawn, one gap added, and a priority order applied.**

This is the strongest Phase 0 output of the sprint. It found two things I got wrong and one thing I asserted without checking. Those are recorded below rather than quietly corrected.

---

## 1. Withdraw gap 5. My brief asked for the wrong thing

My 1.5 brief required explicit deletion of run datasets and tables with an expiry backstop. I wrote that before knowing the connector uses no named destination table at all.

Given what the map establishes, **building the managed design would make the privacy position worse, not better.**

Today: no dataset is created, no named table exists, results land in an anonymous temporary table restricted to the creating service account, and it expires under the provider lifecycle within 24 hours. Nothing durable is created and nothing needs deleting.

The proposed fix: create a dedicated dataset, create a per-run destination table containing client forecast values, then delete it in a `finally` block. That manufactures a durable object holding client data where none exists, adds a failure mode where a crashed run leaves it behind, and buys a deletion call you can point at. It trades a real reduction in exposure for a demonstrable control.

**Do not build it.** Describe the provider behaviour accurately instead: results are written to an anonymous temporary table, access is restricted to the service account that created the job, it expires within 24 hours, and Silurian creates no named object. That is a better answer to a security reviewer than a deletion routine, and it is true.

Two conditions on withdrawing the gap:

- The 24 hour window and the access restriction go in the written statement explicitly. Do not let "no retention" stand unqualified.
- Gap 4 stays. Assert `cacheHit=false` on every production forecast job, not only during measurement.

## 2. Add a gap. Move reopen into the browser

Not in the map, and it removes an entire data path rather than documenting one.

Story 1.4 reopen currently accepts an uploaded bundle. That bundle contains client data by design, so reopening sends SKU identifiers, metrics, findings and forecasts back through Vercel, the multipart spool and function memory, for an operation that computes nothing. The map covers it under item 4, but as a fact rather than as a question.

A bundle is JSON. Parsing it, verifying `bundle_sha256` and the embedded manifest hash, and rendering the recorded results are all doable in the browser with no server involvement.

The gain is not only technical. It produces the strongest single sentence available for the data handling statement: **reopening a run happens entirely in your browser, and the file never leaves your device.** No supplier answering a pharma security questionnaire gets to say that about their own output format.

It also reinforces the 1.4 rule that reopen never recomputes, because a browser-only reopen structurally cannot call an engine.

Raise it as a question if there is a reason the server must see the bundle. I cannot see one.

## 3. Three corrections to my own work, accepted

**The manifest filename.** Correct, and it invalidates the phrase I have used repeatedly. The manifest is data-minimised, not client-data-free, while it carries a client-supplied filename. A filename such as `AcmePharma_Q3_demand_TREDEGAR.csv` identifies the client, the site and the period.

Recommended fix, better than dropping it: replace `source.filename` with `source.filename_sha256` plus `source.extension`. A client can hash their own filename to confirm which file a manifest belongs to, and the manifest carries no readable identity. Carry it on the 1.2 schema bump already in flight, and correct the schema description, which currently states that the filename is permitted.

Only after that does "the proof carries no client data" become a claim you can make.

**The query cache.** I wrote that disabling the cache prevents retention. The map is right: disabling reuse does not prevent a temporary result table existing. My statement was too strong and the corrected version belongs in the written note.

**The region.** I assumed the US default from the 1.3 survey. The connector defaults to `europe-west2`. Good, and it makes the remaining region question sharper rather than softer, see below.

## 5. An asset the map records but does not flag as one

`AI.FORECAST` receives two arrays: dates and demand values. No SKU, no customer, no site, no filename, no descriptions, no commercial context.

That means **the sub-processor never receives identifiers, only anonymous numeric series.** It answers questions 9, 11 and 12 of the security set in one sentence, and it is unusual. Most tools in this space push the whole dataset to their provider.

Say it early in the note rather than burying it in a flow diagram. Paired with the browser-only reopen, and a manifest carrying a filename hash rather than a filename, the position becomes genuinely strong for a supplier of this size.
