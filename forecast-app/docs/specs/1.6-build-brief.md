# Build brief: story 1.6, make the stages agree

Silurian Forecast Diagnostic. Sprint 1 remediation, before sprint 2 starts.

Short brief for a short story. This is a deletion, a correction to my own expectations, and one test. No new capability.

---

## 1. What was found, and whose fault it is

I ran the real fixtures through production. The quality engine is correct in every respect: all twelve bands on `20_portfolio_mixed.csv` match `expected_quality.json`, PKG-30219 comes back clean despite a 68.6 percent zero share, PKG-30220 comes back not usable with the zero versus missing finding, and the headline numbers match to the decimal. The reject path on `02_date_disorder.csv` names both sides of the day-first against month-first contradiction with row numbers. The provenance panel carries a filename hash rather than a filename.

The defect is that **the validation stage and the quality stage describe the same file differently, on the same screen**:

| Subject | Validation says | Quality says | Correct |
|---|---|---|---|
| PKG-30220 | `HISTORY_TOO_SHORT`, "has 8 periods" | 8 of 33 periods, `ZERO_VS_MISSING_AMBIGUOUS` | Quality |
| PKG-30219, PKG-40006 | `ZERO_VS_MISSING_AMBIGUOUS` | clean | Quality |
| PKG-40005 | `SERIES_DISCONTINUED` | `SERIES_STALE` | Quality |

**This originates in my specification, not in the implementation.** Stage F of the 1.1 brief was "series: unit breaks, zeros against gaps, history length, record types", and `expected_findings.json` v1.1 asked for descriptive series findings during validation in four fixtures. Codex built what I specified. When story 1.2 built the same detectors properly, with corrected thresholds from the 1.2 answers, nothing reconciled the two. Two implementations of the same judgement, one of them a version behind.

---

## 2. The rule that resolves it

Not "no series analysis in validation". That would delete the most valuable check in the set.

**A gate decides whether a run may proceed. A characterisation describes what the data is.**

- Proceeding with an **undetected unit change** produces an answer wrong by the pack factor. That is a gate. It stays in validation.
- Proceeding with a **short history** produces a valid answer with limited evidence. That is a characterisation. It belongs to quality.

Applying that line:

**Validation keeps**, because each one blocks:

- `UNIT_SCALE_BREAK_SUSPECTED`
- `UOM_CHANGE_MIDHISTORY`
- `RECORD_TYPE_MIXED` and `FORECAST_ROWS_IN_ACTUALS`

**Validation loses**, because each one only describes:

- `HISTORY_TOO_SHORT`
- `SERIES_DISCONTINUED`
- `SERIES_STALE`
- `ZERO_VS_MISSING_AMBIGUOUS`
- `SINGLE_OBSERVATION_SERIES`

Delete them from validation. Do not fix them to agree with the quality engine. Two agreeing implementations drift apart on the next threshold change, and this is the moment when deleting one is cheapest.

## 4. The test that prevents recurrence

The important half of this story, because it catches the class rather than the instances.

Add to the permanent suite, run over every fixture:

1. **No finding code appears in more than one stage.** Build the set of codes each stage can emit and assert the intersection is empty. This is a static check and can run without any fixture at all.
2. **No two stages describe the same SKU in contradictory terms.** For each fixture, collect every stage's findings by SKU and assert no SKU carries findings from two stages that disagree about the same property.
3. **The rendered page contains each code once.** A cheap end-to-end guard: run the mixed portfolio through the real endpoints and assert no code appears in both the validation block and the quality block.

Check one alone would have caught all three defects. Add it to the permanent definition of done, which the tracker now carries, so it applies to every story from here rather than only to this fix.

## 5. Two copy fixes while you are in there

- **`DATE_FORMAT_AMBIGUOUS` is doing two jobs.** On `02_date_disorder.csv` it appears twice with different meanings: contradictory day and month order evidence, and values whose order cannot be inferred at all. Two conditions, two codes, two messages. Suggest keeping `DATE_FORMAT_AMBIGUOUS` for the contradiction and adding `DATE_ORDER_UNRESOLVABLE` for the second.
- **`31/04/2025` is cited as day-first evidence.** It does not exist under either reading, so it supports no inference. It raises `DATE_INVALID` and is excluded from the evidence set. A reviewer who spots that we used an impossible date as proof of anything will discount the rest of the message.

## 7. Definition of done

- Validation gates. Quality characterises. Nothing does both.
- The consistency test is in the permanent suite, and it has been seen to fail.
- No client reading the page top to bottom encounters the tool contradicting itself.
