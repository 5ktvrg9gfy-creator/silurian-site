## 0. Rules of engagement, changes from 1.1

Everything from the 1.1 brief still applies. Two amendments:

- **Reuse, do not recompute.** Story 1.1 already produces a normalised dataset, a transformation log and a findings list. The quality report consumes those. If you find yourself re-parsing the file, stop and raise a question instead.
- **This story has a client-facing output.** In 1.1 the messages mattered. Here the whole artefact is read by a client, sometimes without you in the room. Copy quality is part of the acceptance criteria, not a polish pass afterwards.

Questions go in `docs/1.2-open-questions.md`, same format: what it blocks, your recommended default, cost if wrong.

## 1. The distinction this story hangs on

Story 1.1 is a **gate**. It answers one question: may this file be used. Its output is per file, and its severities are blocking, warning and information.

Story 1.2 is a **portrait**. It answers a different question: what state is this client's demand data actually in. It runs on files that have already passed the gate. Its output is per SKU and per portfolio, and it has no blocking concept at all.

**The failure mode to avoid is building 1.2 as a re-render of 1.1 findings.** A file can pass validation cleanly and still be poor data for forecasting: short histories, stale extracts, gap blocks from a system migration, half the portfolio too small to matter. None of that is a validation error and all of it changes what the diagnostic can honestly claim.

Commercially, this is the first artefact you can put in front of a client. It converts "your data is a mess" from an opinion into an evidenced finding with a number attached, and it does that before any forecast exists. That is why it sits in sprint 1 rather than later.

---

## 2. Scope

**In scope.** Coverage and continuity per SKU, zero and intermittency facts, volume concentration, variability, outlier candidates, level shifts, staleness, and a portfolio summary that weights all of it by volume. A quality band per SKU and for the portfolio. An exportable report object.

**Out of scope.** Demand classification into smooth, erratic, intermittent and lumpy, which is story 2.1. Method routing, which is 2.4. Any judgement about whether a series is forecastable, which is 2.3. Any correction of the data.

**The boundary, stated precisely.** 1.2 computes and exposes the metrics. 2.1 applies thresholds to them and assigns classes. Compute ADI and CV squared here, because 2.1 needs them and computing them now makes that story nearly free, but **do not classify**. A metric is a fact. A class is a judgement.

## 4. Metrics

All computed per SKU at the file's grain. Grain is inferred from the modal spacing between periods and reported explicitly, with a user override. Everything below assumes monthly for readability.

### Coverage and continuity

| Metric | Definition |
|---|---|
| `first_period`, `last_period` | Bounds of the series as supplied |
| `periods_present` | Count of periods with a row |
| `periods_expected_in_span` | Calendar periods between first and last inclusive |
| `gap_count` | Expected minus present |
| `longest_gap` | Longest consecutive run of missing periods inside the span |
| `coverage_pct` | Present divided by expected |
| `trailing_gap_periods` | Periods between `last_period` and `as_of_date`, exclusive |

### Demand shape

| Metric | Definition |
|---|---|
| `zero_periods`, `zero_share_pct` | Recorded zeros, not missing periods |
| `longest_zero_run` | Longest consecutive run of recorded zeros |
| `adi` | Periods present divided by count of non-zero periods |
| `cv_squared_nonzero` | Squared coefficient of variation of non-zero demand values |
| `mean`, `median`, `cv` | On all present periods |

### Materiality

| Metric | Definition |
|---|---|
| `volume_total` | Sum across the series |
| `volume_share_pct` | Share of total portfolio volume |
| `rank_by_volume` | Descending |
| `cumulative_volume_share_pct` | For the Pareto view |

Value weighting rather than volume weighting is better where unit cost is available, but cost inputs do not arrive until story 4.1. Use volume now, and structure the code so a cost column swaps in later without reworking the report.

## 5. The four detectors

### 5.1 Outlier candidates

Robust methods only. A mean and standard deviation approach fails on exactly the series that matter, because the outlier drags both.

```
if periods_present >= 24:
    deseasonalise by dividing each value by the median for its month-of-year
else:
    use raw values

modified_z = 0.6745 * (value - median) / MAD        // MAD = median absolute deviation
flag when |modified_z| > 3.5                         // Iglewicz and Hoaglin
if MAD == 0: fall back to an IQR rule, do not divide by zero
```

**The hard requirement.** A genuine seasonal peak is not an outlier. Fixture `22_outliers_and_shift.csv` contains `SKU-SEASONAL`, which triples every December in all three years. Flagging it is the single most common defect in naive implementations, and a client planner will spot it in seconds. The deseasonalising step exists for that case.

Outliers are **candidates**, never removals. The report names them and says what a planner should check: a promotion, a stock build, a one-off tender, a data error.

### 5.2 Level shift

A sustained change in level, distinct from the unit break already detected in 1.1.

```
same split search as brief 1.1 section 6.4
flag LEVEL_SHIFT when the ratio is sustained for >= 3 periods
and the ratio is NOT within 12% of a pack factor
```

If the ratio does match a pack factor, 1.1 has already raised it as a unit break and blocked the run. Here you are catching the other case: a real change in the business, such as a new customer, a lost tender, or a transfer between sites. Fixture `22` has one at 1.6 times, deliberately not a pack factor.

Level shift is not an error. It is a warning that history before the break may not represent the future, which matters for how much history the forecast should use.

### 5.3 Suspect zeros

A recorded zero inside an otherwise continuous, non-intermittent series is usually a stockout or a missed posting, not zero demand. Two very different things: a stockout is censored demand and understates the truth.

```
flag SUSPECT_ZERO when a zero appears in a series with
  zero_share_pct < 10 and adi < 1.25
```

Do not flag zeros in intermittent series. That is their normal behaviour, and that judgement belongs to story 2.1 anyway.

### 5.4 Staleness

Two levels, and conflating them is the failure mode.

- **Extract level.** If most series end at the same period and that period is well before `as_of_date`, the extract is stale. This is **one finding about the file**, not one per SKU. Fixture `21_stale_extract.csv` exists purely to test this. Reporting four identical staleness findings there is a fail.
- **Series level.** If an individual series ends materially before the rest of the portfolio, that series is discontinued or dormant. Fixture `20` contains both a discontinued line and a stale one.

## 6. Banding

Per SKU and for the portfolio. Three bands, not a score.

| Band | Meaning |
|---|---|
| `clean` | No quality findings. Suitable for the diagnostic without caveat |
| `caveated` | Usable, with named limitations that must appear in the report |
| `not_usable` | Cannot support a forecast conclusion. Reported, and excluded from headline claims |

**Do not build a 0 to 100 quality score.** It looks precise, it is arbitrary, and the first client who asks how it is calculated will be told a weighting you invented. Three named bands with explicit criteria survive that question. If you disagree, raise it rather than building one.

The portfolio band is not the average of the SKU bands. It is driven by volume: a portfolio where every flagged SKU is immaterial is a clean portfolio with footnotes.

## 7. The report

The point of the whole story. Structure it for a reader who sees it before they see a forecast.

**Headline, three numbers.** SKUs analysed, periods covered, share of portfolio volume with clean data.

**The finding that does the work.** Report every portfolio statement twice, once as a share of SKUs and once as a share of volume. On fixture `20`, 8 of 12 SKUs carry a quality finding, which is 67 percent of the portfolio, but those SKUs carry only 16 percent of the volume. Both numbers are true and they tell opposite stories. Showing only the first is alarmist. Showing only the second is complacent. **Showing both is the finding**, because it tells the client where to spend attention, and it is the sentence that gets repeated in their own meeting after you leave.

**Per SKU table.** Sorted by volume descending, not alphabetically. Coverage, periods, zero share, last period, band, findings.

**Exception list.** Only SKUs that are `caveated` or `not_usable`, each with the finding, the materiality, and what the client would have to do about it.

**Method note.** Grain, `as_of_date`, thresholds used, and the fact that outliers are candidates rather than corrections.

Copy rules from the 1.1 brief section 7 still apply. One addition: the report says what the data allows and what it does not. Never apologise for the client's data, and never imply the tool has fixed anything.

**Export.** A JSON quality object, and a printable HTML view. The branded PDF is story 5.1, so do not build it here, but keep the report object clean enough that 5.1 can render it without rework.

## 8. Fixtures and acceptance

Four files, three of them new. All pass 1.1 validation, so any validation finding here is a regression.

| File | Purpose |
|---|---|
| `00_clean_control.csv` | No quality findings at all. Declares its own `as_of_date` of 2026-01-01 so staleness does not fire |
| `20_portfolio_mixed.csv` | Twelve SKUs, eight quality problems, three clean lines carrying 83 percent of volume. The flagship demo file |
| `21_stale_extract.csv` | Every series ends four periods early. One extract-level finding, not four |
| `22_outliers_and_shift.csv` | Seasonal peak that must not flag, a true spike that must, a level shift that must not be read as a unit break, and a suspect zero |

`expected_quality.json` carries exact structural metrics generated from the fixture data, with tolerances, plus `must_flag`, `must_not_flag` and `must_not_raise` assertions.

Assertions:

1. Every structural metric matches within tolerance.
2. Every `must_flag` code appears for its SKU.
3. No `must_not_flag` SKU carries any quality finding.
4. `SKU-SEASONAL` raises no outlier candidate. Assert this one explicitly, it is the regression that will come back.
5. `SKU-LEVELSHIFT` raises `LEVEL_SHIFT` and not `UNIT_SCALE_BREAK_SUSPECTED`.
6. `21_stale_extract.csv` raises exactly one extract-level staleness finding.
7. On `20_portfolio_mixed.csv`, the report states both the SKU share and the volume share of flagged items, and they differ by more than 40 points.
8. No validation regression on any of the four files.

---

## 9. Definition of done

- All eight assertions pass.
- The control file produces an empty findings list and a `clean` portfolio band.
- Nothing is recomputed that 1.1 already produced.
- The quality object is serialisable and carries the grain, the `as_of_date`, the thresholds used and the metric values, so a finding can be defended a week later from the record alone.
- The per SKU table sorts by volume by default.
- ADI and CV squared are computed and exposed, and nothing in this story classifies on them.
- A reader who has never seen the tool can read the report and say what they would do next.
