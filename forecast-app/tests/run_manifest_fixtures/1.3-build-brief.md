# Build brief: story 1.3, run metadata stamp on every output

Silurian Forecast Diagnostic. Sprint 1, story 1.3. Follows completed stories 1.1 and 1.2.

Same phases and question protocol as before. Two files ship with this brief: `run_manifest.schema.json` is the target, and `run_manifest.golden.json` is a worked example over `20_portfolio_mixed.csv` with real hashes.

---

## 1. What this story actually is now

The backlog wrote 1.3 as "model version, parameters, horizon, dataset hash and timestamp printed on screen and in the export". Stories 1.1 and 1.2 have since built most of the pieces: a validation record with the source hash and every user decision, and a quality result with thresholds, grain and `as_of_date`.

So 1.3 is no longer about collecting metadata. It is about **binding it into one chain that proves what produced a number**.

Three things are missing today, and they are the whole story:

1. **The chain.** The validation record and the quality result exist separately. Nothing proves the quality result was computed from that validation output rather than some other run.
2. **The model.** Nothing records which model, which weights, which context length and horizon produced the forecast. That is the one stage nobody can reconstruct from the inputs.
3. **The honest reproducibility position.** Nothing states which stages are reproducible and which are not.

**The question the manifest answers:** a client disputes a number nine months from now, their data is long deleted, and you have to say exactly what produced it. If the manifest cannot answer that alone, this story is not done.

---

## 2. The chain integrity rule

This is the mechanism that makes the manifest worth anything.

```
stage[0].input_ref.sha256  ==  source.sha256
stage[n].input_ref.sha256  ==  the sha256 of the artefact it consumed
```

Both the quality and forecast stages consume the normalised dataset, so both reference the same hash. The validation stage consumes the source file. `integrity.chain_verified` is true only when every reference resolves.

A manifest whose chain does not verify is worse than no manifest, because it looks authoritative. Fail the run rather than emitting one.

Hashing rules, and they must be exact or the chain breaks on trivia:

- Artefacts are hashed as **canonical JSON**: keys sorted, separators `,` and `:`, no insignificant whitespace, UTF-8.
- The source file is hashed as raw bytes, before any decoding or BOM strip.
- `integrity.manifest_sha256` is the SHA-256 of the manifest with that field set to the empty string, canonicalised the same way. The golden example was generated this way, so match it.

---

## 3. The manifest carries no client data

**Design rule: the manifest contains hashes, counts, options and outcomes. No SKU identifiers, no demand values, no descriptions.** The only client-controlled string in it is the source filename.

This is not tidiness. It resolves a tension left open in story 1.1. The data handling position says nothing is retained, which is what makes the tool easy to get past a client's IT function. A provenance record that carried SKU codes would contradict that and would have to be deleted along with everything else, which defeats its purpose.

Because the manifest holds nothing belonging to the client, it can be archived indefinitely by both sides. That is a genuinely useful property in a regulated industry, and it is worth saying out loud in the report: **we keep the proof, not the data.**

Assert it in a test. Scan the serialised manifest for any SKU identifier appearing in the source file and fail if one is present.

---

## 4. Model identity

The part nothing currently records, and the part that cannot be reconstructed later.

Required: family, version, checkpoint, context length, horizon. Recommended and expected in practice: frequency indicator, quantiles, backend, precision, preprocessing, series included and excluded with reasons.

**`checkpoint` must be a weights identifier or revision hash, not a friendly name.** "TimesFM 2.0" is not an answer to which weights produced this number. Model repositories move, and a friendly name silently points at different weights over time. Pin the revision and record it.

Record exclusions and why. On the golden example, 9 of 12 series were forecast: 2 excluded by the `not_usable` band from story 1.2, 1 for insufficient context. A client reading a portfolio report needs to know a quarter of their lines were not modelled, and the manifest is where that count is defensible.

The golden example carries `REPLACE_WITH_ACTUAL` in the model and environment blocks. Fill them from the real deployment. A manifest that ships with those strings in it is a failed test, so assert on that too.

## 5. Reproducibility, stated honestly

Validation and quality are pure functions over their inputs. They are bitwise reproducible and the manifest should say so.

The forecast stage is different, and this is where the temptation to overclaim sits. Foundation model inference is not automatically bit-identical across hardware, backends, batch composition or library versions. It may be stable in your deployment. It may not be. **You do not know until you measure it, and the manifest must not imply you do.**

The `determinism.class` field takes three values:

- `bitwise`, identical output guaranteed for identical input in this environment. Only after measuring.
- `tolerant`, reproducible within a stated tolerance. Requires `tolerance_pct`.
- `unknown`, not yet measured. The golden example ships as `unknown` deliberately.

**Task for this story: measure it.** Run the same input through the forecast stage twice on the same deployment, compare outputs, and set the class from what you observe. If they differ, quantify by how much and set `tolerant` with the figure. If they are identical across ten runs, set `bitwise`.

Do not leave it at `unknown` once the diagnostic is being sold. A client asking "if you ran this again would you get the same answer" deserves a measured answer, and "yes, within 0.3 percent" is a perfectly good one. "Yes" when you have not checked is not.

---

## 6. Where the manifest appears

- **On screen**, as a compact provenance panel: run id, source filename and hash prefix, `as_of_date` and its source, model and checkpoint, and the reproducibility statement in plain English. Not a JSON dump.
- **In every export**, so the quality report and later the diagnostic report each carry the run id and manifest hash in the footer. A page that leaves the building must be traceable to the run that produced it.
- **As a download**, the full manifest as JSON.

Copy note. The reproducibility statement is client-facing and must survive being read by someone technical on their side. Say what is reproducible, what is not, and what has not been measured. Understating is safe. Overstating is the one thing that cannot be walked back.

---

## 7. Acceptance

1. Schema conformance. Every emitted manifest validates against `run_manifest.schema.json`.
2. Chain integrity. Every `input_ref` resolves to the preceding artefact. A deliberately corrupted reference sets `chain_verified` false and fails the run.
3. Hash stability. The same file and options produce the same `manifest_sha256`, excluding the timestamp fields. Vary `created_at` alone and confirm the artefact hashes do not move.
4. No client data. The serialised manifest contains no SKU identifier from the source file.
5. No placeholders. No `REPLACE_WITH_ACTUAL` string reaches a real manifest.
6. Options completeness. Every effective option appears, including defaults applied silently. A run where the user set nothing still records the full option set.
7. Determinism measured. `determinism.class` for the forecast stage is `bitwise` or `tolerant`, with a figure, and the measurement is recorded in `docs/1.3-determinism.md`.
8. Export propagation. The quality report export carries the run id and manifest hash.
9. Golden comparison. Running the pipeline over `20_portfolio_mixed.csv` produces a manifest structurally identical to `run_manifest.golden.json`, allowing for real values in place of placeholders and real timestamps.

---

## 8. Definition of done

- One manifest per run, chained, schema-valid, and emitted for every run including rejected ones.
- A rejected run still produces a manifest. A client who was told their file could not be used is entitled to the same evidence as one who was not, and the validation passes are the record of what was asked and answered.
- The manifest alone answers what produced a number, without the source data.
- The reproducibility statement is measured, not assumed.
- No client data in the manifest, asserted by test.

## 9. Note on where this leads

Two later stories depend on this being right, so it is worth building properly now rather than retrofitting.

Story 5.4, the method and limitations appendix, is largely a rendering of the manifest plus the quality method note. Story 7.1, run over run comparison, is a diff of two manifests and their artefact hashes. If the manifest is complete, both become small. If it is thin, both become archaeology.
